# 原生接入到底怎样工作

更新：2026-10-13，0.6.0。

## 不只是把接口名称聚合起来

API 给出实际源码位置、原函数／类方法、构造器、初始化顺序、资源和内部边界。引擎检查这些声明能否对应真实源码，再建立参数接口与调用绑定。执行时使用原 callable、原对象和原返回关系。

不是把完整算法交给模型重新写一遍。生成的代码集中在调用外层的门禁、SDK 注册前接线，以及有限规则允许的局部循环体提取；原算法仍然执行。

## Unit、owner 和 controller

| 概念 | 直白含义 |
|---|---|
| Unit | 能力池中一个具备实际参数接口的可调用入口 |
| owner | 持有原模型、会话、工具、状态和初始化结果的对象／运行宿主 |
| controller | 原 Harness 内决定分支、迭代、下一步和结果汇合的控制逻辑 |
| 内部边界 | 原 controller 到达时进入调度的调用发生，不必是对外独立能力 |

一个 Harness 可以产生多个 Unit。同一个原对象中的多个入口可能共享 owner；内部一个方法还可能存在多个门控位置。共享对象不能被当成无状态函数复制。入口必须能绑定所需初始化和参数，内部步骤只有被原 controller 使能后才会进入调度。

## W、H、R 实际做什么

| 操作 | 实际代码行为 | 原型范围 |
|---|---|---|
| W：包装 | 保存原 callable，在调用外层等待许可，再调用原实现，保持返回／异常路径 | 有真实源码、签名和 owner 的同步／异步 callable |
| H：原生接线 | 在原生工具列表交给 SDK 前安装代理，使实际原流程经过门控 | 引擎能定位并支持的注册锚点；未知 SDK wiring 明确缺失 |
| R：有限局部重构 | 将指定循环体变成原 owner 上的受控方法，原循环仍按原序逐项调用 | 顶层类的 async 实例方法中顶层 `for`，直线赋值／调用体 |

R 不接受 `break`／`continue`／`return`、嵌套控制流或词法作用域、跨轮标量回写、循环体局部变量向后存活、反射等结构。引擎检查提取和逆向结构，不接收模型生成的替代算法。它不会把顺序循环直接改成并行。

同一方法“整体 W”与“内部 R”是替代粒度，不能重复门控为同一个同时激活方案。父 controller 若等待内部受控调用，不占住内部调用需要的执行槽。

## 与数据、配置和模型有关的情况

目录中的文本配置和源码可以成为分析证据；模型权重、数据集、图像等二进制保持为资源引用。初始化和函数参数按原 Harness 接口绑定这些实际路径。原目录、Notebook 其他单元和数据不由模型改写为另一套内容。

如果入口需要一个真实 SDK Model／Context 对象，而接入范围内没有已支持的构造与绑定方式，入口是 `MISSING`。缺少文件或依赖也明确报缺失。不会用字符串伪装原对象，也不会编造一个“通用 Harness”替代原实现。

Notebook 接入使用受支持的定义、导入和字面值，不自动执行整本中的顶层样例调用。需要未绑定的非字面值全局对象时，仍然报缺失。

## 怎样进入实际对话

只有可绑定的原生入口加入对话工具目录。API 在对话时按实际参数接口提出方案，上层 RL 选择完整方案；进入原生入口后，原 controller 决定实际哪些内部边界发生，下层 RL 决定这些已使能调用何时获准开始。

能力拆分与部署拆分分开。当前平台以一个进程／容器承载原生对象，没有把每个 Unit 单独部署成服务。将来讨论 K8S 时，部署单位必须围绕 owner 的原状态和生命周期；仅按函数切 Pod 无法保持共享对象和继续关系。
