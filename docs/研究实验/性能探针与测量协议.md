# 性能探针与测量协议

本文规定系统性能和调度实验如何观察、保存与解释证据，2026-11-02 按 0.15.5 的实际运行补充结果判据。研究问题是在原防护效果满足要求的前提下，比较相同工作量与原方法配置下的资源及调度表现。本文是测量方案；未标明已有的接口和结果均为待实现或待实测，任何数值不预设。沿用既有 RL 特征、奖励和动作理论；探针首先作为独立证据，不改变训练信号。

## 1. 已有能力与待补证据

`resource_observation.py` 已有显式配置的窗口观察器 `WindowObserver`，采集指定 PID、cgroup v2 和 GPU UUID，记录原始 JSONL 与汇总 JSON；支持动态 PID 和受管资源采样、阶段标记、采样失败及覆盖率。`resource_process.py` 采集单进程 CPU 累计时间与 RSS，以及指定 cgroup 的 CPU 和内存；不会自动遍历进程树。`joint.py` 已在窗口准备前启动观察器，标记 preparation、workload、release 等阶段并在结束时生成资源摘要。实际覆盖取决于所选对象、动态解析与释放状态，不由接口名称保证。

另有独立的 `ResourceMonitor`，默认关闭，用户在运行观察页选择指标后启动；它支持实时资源记录和导出，且不修改正式窗口观察器的配置或 RL 奖励。它记录当前平台进程、平台本会话拥有的 Docker worker 和受管服务 cgroup，以及显式选择的已配置 GPU 整卡，不自动包含其他子进程、远端 API 或其他主机。K8S 容器计数暂不支持。受管服务 cgroup 统计属于该实例范围，不能推断 GPU 显存；整卡采样属于设备范围。窗口观察器提供有效时间、覆盖、积分和采样峰值，阶段标记本身不触发采样。独立监控记录采样耗时、有效区间和采样峰值；其运行记录不自动成为正式实验窗口的任务级归因证据。

## 2. 观察窗口与任务事件

每次运行记录 `run_id`、实验组、工作负载和重复编号，以单调时钟计算时长，用 UTC 时间对齐人工记录；跨主机不直接相减单调时钟。观察器在任何 prepare/load 前启动，覆盖工作负载、hold 和 release，直到确认资源释放后结束；未确认释放时记录 `release_unconfirmed` 与观察截止时间，不宣称完整生命周期。固定窗口还需声明进入时已有的服务、缓存、预热状态及退出后仍保留的资源。

阶段事件至少包含名称、对象/实例及代次、起止时间、结果和原因。prepare 是准备动作发起到完成或失败；load 是加载动作发起到完成或失败；hold 是资源实际保有期间，按获得到确认释放界定；release 是释放请求到确认释放或观察截止。重叠阶段分别计时，不相加冒充端到端时间；未发生、失败和时间点未知分别标识，不能用零填充。阶段内资源值仅在采样与边界足以支持时单独计算，不能因标记存在就声称准确截取。

每个任务记录提交、进入可调度队列、首次合法就绪、派发、执行开始、终态及重试/超时事件；各时间点须注明实际来源。端到端延迟为终态减提交，队列等待为派发减入队，并区分依赖未就绪等待与合法就绪后等待；执行时长为终态减执行开始。缺少事件的分项标记未知。记录失败与超时的延迟和未完成数量，不能只报告成功任务的尾延迟；成功任务的 p50/p95/p99 需注明样本量与分位算法。

## 3. 指标、来源和解释

| 指标 | 测量与用途 | 口径 |
| --- | --- | --- |
| 任务质量/防护效果 | 按场景使用既定两层评价和原方法判据，保存评价版本及可评价数 | 报告各指标的有效分母、缺失和失败；保护效果约束与资源收益同时呈现 |
| 完成与失败 | 记录提交、成功、失败、超时、取消、观察截止未决；保存终态原因 | 成功率以全部提交任务为分母，给出各类计数；评价有效率另用可评价任务为分母；重试与逻辑任务分开 |
| 延迟与队列 | 事件差计算端到端、队列、就绪后等待、执行时间；记录队列长度随时间 | 每个分布说明总体、单位及样本数；队列长度按时间加权，记录高峰为采样峰值 |
| 吞吐 | 指定稳态或完整窗口的成功完成数 / 窗口秒数，同时给全部终态数 / 秒 | 声明到达模式、窗口边界、排空策略和未完成任务，防止短窗口截断造成偏差 |
| CPU | 单进程 user+system 或 cgroup `cpu.stat usage_usec` 累计计数差 / 有效时间，单位核；累计差单位 CPU 秒 | 相邻有效点同身份、计数不倒退且间隔不超阈值才计算；多核可大于 1，百分比需声明归一化核数。CPU 秒是有效区间计数差之和，不是百分比样本相加 |
| 内存 | 进程 RSS/Windows 工作集，或 cgroup `memory.current`，记录字节、采样峰值及时间积分 byte·s | 两者语义不同，不能互换。cgroup 含后代和页缓存等计费内存，不等于进程 RSS 或模型私有内存；进程与包含它的 cgroup 不重复求和 |
| GPU | 指定 UUID 整卡显存、GPU 利用率和功率；记录采样峰值、有效覆盖及显存时间积分 | 共享设备计入其他进程及背景活动；设备利用率为设备采样窗口内有 kernel 活动的时间比例，不是任务 GPU 秒。进程显存仅在接口真实可用时另列，不能据此拆分整卡利用率 |
| 功率/能量 | 整卡功率 W 在有效相邻采样点做梯形积分得到估计 J；若另采设备累计能量，报告计数差与重置 | 均为设备范围，非任务能耗；未知或不支持不填零。功率可能是设备提供的时间平均值，须记录设备、驱动及接口语义 |

Linux 官方规定 cgroup CPU 统计覆盖后代，`memory.current` 是 cgroup 及后代的当前内存；内存计费包括页缓存等，参见 [Linux cgroup v2](https://docs.kernel.org/admin-guide/cgroup-v2.html)。[NVIDIA NVML 设备查询](https://docs.nvidia.com/deploy/nvml-api/latest/api/group__nvmlDeviceQueries.html) 说明功率读数与架构相关，设备累计能量自驱动重载以来累计；[NVML 采样类型](https://docs.nvidia.com/deploy/archive/R550/nvml-api/group__nvmlDeviceStructs.html) 说明 GPU 利用率是执行 kernel 的时间比例。可用性和设备共享状态以实际运行记录为准。

## 4. 采样质量和归因

采样时记录配置间隔、实际采样起止及耗时、各来源时间戳、状态和错误；观察间隔包括采集本身可能带来的延迟。相邻有效采样间距超出冻结阈值时不跨缺口积分，也不将缺失插值为零。现有窗口汇总采用 2.5 倍配置间隔作为最大积分间隔；报告各指标有效时间 / 窗口时间、样本数、最大间隔和缺口，冻结正式实验可接受覆盖阈值及不足时的处理。采样峰值只能称为 sampled peak，短于间隔的突发可能漏掉。资源积分为有效区间的梯形估计；覆盖不足时保留部分值及覆盖，不能外推为完整窗口总量。

身份变化、计数器重置、读取失败、权限不足、GPU 不支持及采样线程未结束均记录为未知或不完整。PID 应连同进程身份防止复用混淆；cgroup 及受管服务记录实例代次，重建前后不直接相减。单进程、cgroup、整卡及远程服务分别展示，重叠范围不相加。远程 API 的服务端资源和账单须另有证据；不能由本地客户端测量替代。墙钟与单调时钟的对齐误差、不同主机的采样位置和共享负载也应记录。

## 5. 实时观察、记录与导出契约

沿用平台观察面板及现有运行记录，不建立独立测试平台。`/inspect?view=operations` 已支持选择八项指标：平台进程 CPU/内存、受管容器 CPU/内存、GPU 整卡显存/利用率/功率、任务与调用；可设置标签、0.5–3600 秒采样间隔和显式配置的 GPU UUID。不可用指标禁选；可选并不保证采样权限或读数可用，实际未知值和原因随记录显示。监控任务与调用统计针对平台状态，其中已完成任务数和延迟分布以监控开始后结束的任务为范围，未完成任务不纳入该分布，不能直接作为第 3 节的正式实验全提交任务分母。

记录启动后后台按所选配置采样并实时追加私有 JSONL；面板读取样本、显示最新值、曲线、采样峰值、有效样本和采样耗时，可选最近 30 条记录。读取和导出不改变调度，但启用采样本身有开销。JSON 导出会话配置与摘要，JSONL 导出已有原始样本；运行中导出是当时截取，不代表完整运行。停止请求后采集线程仍可能处于 `STOPPING`，结束后为 `COMPLETED`；平台重启将遗留的运行中/停止中记录标为 `INTERRUPTED`。原始记录含本机资源身份，分享前应去标识化。

现有接口为：`GET /api/monitor` 获取能力、当前状态和最近会话；`GET /api/monitor/sessions/{id}?offset=&limit=` 读取记录；`GET /api/monitor/sessions/{id}/export?format=json|jsonl` 导出；`POST /api/monitor/start` 接收 `metrics`、`interval_s`、`gpu_uuids`、`label`，`POST /api/monitor/stop` 接收 `session_id`。运维预检另由 `GET /api/operations/preflight?operation=update|source_environment&source_id=` 提供，不是性能测量接口。详情支持分页；面板请求最近 60 条，活跃会话使用有界内存缓存，历史记录及较大请求可从记录文件读取。显示窗口内峰值与完整记录摘要中的峰值各自有不同范围。

正式实验仍需关联 `run_id`、实验组、工作负载/任务 ID、阶段、来源及范围、对象身份/代次、单调和 UTC 时间、值与单位、状态/缺失原因及采样耗时；汇总应附有效覆盖、间隔阈值、样本数、采样峰值和结果版本。现有独立监控会话与正式窗口各有记录，尚不能据此宣称统一任务事件、质量结果和资源归因导出已完整实现。资源记录与任务事件通过运行及时间关联；时间重叠不等于因果归因。

## 6. 实验对照与冻结

1. **主对照**：固定来源版本、模型/权重、输入与任务数、到达轨迹、并发、资源限制、评价、预热/缓存、窗口与硬件，比较既定基线及 RL 调度；记录各组实际执行、失败、输出和质量。若调度使实际执行路径变化，单独报告调用次数、失败、取消和有效工作量，不能将差异称为纯调度收益。
2. **拆分或路径对照**：记录相同输入及要求，核对实际调用和任务完成情况。保持等工作量时可比较效率；若能力路径、质量或完成工作量变化，标为不同路径结果，同时给质量与工作量，不混入同工作量结论。
3. **背景对照**：同设备、同窗口、同服务/缓存状态采空载 baseline，反映背景消耗；另做相同负载下各策略对照。空载相减仅为设备级差分估计，不能解释为某任务能耗，且需披露背景波动和共享设备。
4. **探针开销**：相同策略、配置、工作负载和环境，配对运行无探针与有探针，按预先固定的顺序/重复方案报告任务完成率、延迟、吞吐和可获得的独立资源差异；无探针组资源测量若无独立仪表则为未知，不能使用有探针组的采样代填。探针自身查询耗时及频率一并记录。运行顺序、重复数与统计汇总在执行前冻结，保留失败及中止样本。

正式运行前冻结 `formal_experiment_config`（名称以实际配置接口为准）：来源/构建及完整方法、策略和权重版本；数据和任务轨迹；资源、服务及初始缓存状态；评价和成功/失败定义；窗口、阶段、排空与释放；观察对象、采样间隔、有效覆盖及缺口阈值；组别、重复、顺序、随机种子与统计方法。记录配置快照和身份摘要，变化产生新配置并分别报告。观测数据是独立实验结果；不得悄然用作新的 RL 特征或奖励。

结果表至少按组列出提交/成功/失败/超时/未决、质量及有效分母、延迟分布和样本量、队列等待、成功吞吐、CPU 秒、内存 sampled peak 与 byte·s、整卡显存 sampled peak 与 MiB·s、设备能量估计、各指标覆盖和探针开销。所有未经真实运行验证的值均为待测；不能凭静态 READY、演示或模拟运行填入正式结果。

## 7. 同输入配对、产物观察与独立评分（2026-11-02）

真实开发运行暴露了两种必须分开的情况：RefChecker 旧平台批次的部分参数被对话模型改写，即使最终标签与原生返回相同，也不能计为同输入成功；TruFor 的目录读取权限不足曾表现为遍历得到零个文件，之后只读核验确认两份 NPZ 实际存在且结构有效。前者是输入一致性失败，后者是观察失败。详细批次结论统一维护在[来源核验记录](../设计与实现/分析器共性缺口与验证.md#15-0154-九来源完整结果复查与绑定恢复2026-11-02)，这里规定所有来源共用的判据。

每个逻辑任务保留以下相互独立的事实；整体状态不能覆盖这些字段：

| 核对项 | 必需证据 | 不足时如何解释 |
| --- | --- | --- |
| 输入一致 | 冻结样本 ID、字节或规范化内容摘要、实际入口参数及模型／配置身份；规范化规则在执行前确定 | 参数改变记输入一致性失败，预测碰巧相同不能补回；只有请求文本而无实际参数依据时保持未核对 |
| 原调用执行 | 实际目标、开始次数、返回／异常／取消及必要调用记录 | 静态 READY、容器存活或进度条不代表目标完成；原代码捕获异常后继续仍逐项检查 |
| 产物可观察 | 输入到输出的命名关系、完整枚举或逐项读取状态、字段／形状／数值与文件摘要，以及旧产物和本次变化 | 成功读取后确认缺失才记缺失；权限、挂载或读取错误记观察未知，不能伪装成缺文件、无预测或零成本 |
| 独立质量 | 冻结标签及评分器、ID 对齐、实际预测、逐项得分与跳过原因 | 文件结构有效不等于预测正确；未取得标注或评分器时不填质量分数 |
| 生命周期与成本 | 实例及代次、准备／执行／驻留／释放的实际事件，资源观察范围与覆盖 | 执行终态和资源释放分别确认；缺观测不意味着零消耗，也不能抹掉失败消耗 |

单文件返回与目录批处理使用同一原则，但检查对象不同。单文件契约明确输入及确切输出路径；目录批处理先冻结输入清单，再依据原代码的命名、跳过和续跑语义建立逐项对应。文件数量相等仍可能存在重复、错配或旧结果，必须核对 ID 和关联。无法恢复目录映射时保留契约缺口，不以猜测后缀替代源码依据。平台现有 `native-completion/1` 只支持有限单文件契约；此次 TruFor 目录核验是独立检查，不能据此宣称平台已通用支持批量完成契约。

研究记录中，令 `I` 表示输入一致性已证实，`X` 表示所声明原目标已完成，`O` 表示预期结果已充分观察并正确关联，`Q` 表示独立评分满足预先冻结的任务判据。对“在共同终点内正确完成”的计数，仅计 `I ∧ X ∧ O ∧ Q` 已证实的任务。任一未知仍留在全到达分母中，并按原因另列；该计数不是对任意防护指标的替代，accuracy、F1、定位指标等仍按原评分语义报告。空主张、空输出等合法原结果按冻结任务判据处理，不能因为数组为空自行判失败。

成本与上述成功计数分开：失败、取消、输入漂移和结果不可观察任务已经花费的准备、执行及驻留成本均保留。不能删除这些任务后再声称相同工作量下资源更少；观察缺口只限制成本结论，不改变实际到达数。B0 与平台臂使用同一任务清单和终点，分别报告执行失败、输入不一致和观察未知，防止把诊断工具缺陷算作原防护质量下降。

结果写出、原 owner 结束和资源释放按各自契约发生。若结果已可在实例之外取得且原调用、owner 和依赖租约均允许结束，可按既有合法动作释放计算实例，随后离线评分；不为等待独立质量报告而强制保留模型。反之，结果仍只在容器临时层或原进程内时，不能先释放再假定后续可读。单文件结构检查、外部核验和离线评分均不会自动解除 W／H／R、owner 或生命周期义务。

当前接线：显式方案接口可避免模型转抄冻结参数；独立核验可检查实际返回及产物。本地 `completion.py` 已将调用后的文件读取错误记为 `UNKNOWN`，保留原 `CompletedProcess`；无法读取输入时不声称输入改变，无法核验输出时 `valid_items` 为未知，已知的非零退出仍保持 `INCOMPLETE`。该修复尚未部署，不能倒算为本次远端实验已使用的功能；本地相关核验见[当前实现](../设计与实现/当前实现.md#本地待部署完成检查的读取错误2026-11-02)。统一的批量结果观察状态仍未完整接入。本节不新增奖励、质量阈值或已验证的调度收益。
