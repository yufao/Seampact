# 0.10.0 异构 Harness 运行环境

本版让平台与 Harness 分别使用自己的 Python 环境。平台进程及默认平台镜像保留 Python 3.11；来源可选择 Python 3.10、3.11、3.12 或 3.13，用匹配解释器执行原源码核对，再为运行组构建包含原依赖的镜像。同一运行组仍在同一进程保留原对象、共享状态、控制流程及 owner；选择不同镜像不会产生新的合法拆分边界。

## 1. 环境选择的依据

来源接入后，平台从已冻结的原库文件读取环境事实，不导入、运行原库或调用分析模型。这些事实附有原相对路径、行号、文件摘要和项目作用域：

| 原文件 | 读取的事实 | 本版处理 |
|---|---|---|
| `pyproject.toml` | `project.requires-python`、Poetry Python 要求、原项目目录 | 硬性 Python 约束；安装项目时保留原项目构建声明 |
| `setup.cfg`、`setup.py` | 静态 `python_requires`、原项目目录 | 只读取可静态确认的声明，不执行 `setup.py` 来发现要求 |
| `.python-version` | 作者使用的明确版本 | 版本 pin 提示，不能覆盖硬性 Python 要求 |
| README／安装说明 | 明确出现的 Python 版本 | 推荐信息，不代替硬性要求 |
| requirements 文件 | 原依赖清单路径 | 提供安装候选，保留文件内容和相对引用 |
| `environment.yml`／`.yaml` | Conda Python 声明及原文件位置 | 保留原依据；需要已准备该环境的基础镜像，不自动转写为 pip 依赖 |
| Dockerfile | 原 `FROM` 镜像及行号 | 供选择和核对；不自动执行原 Dockerfile、多阶段构建或原安装命令 |

根项目和子项目分别保存作用域，独立子项目的 Python 要求不会自动合并。选择原项目子目录后，保存时重新核对该作用域。多份 requirements、项目安装与 requirements 同时存在、多阶段镜像或无法解释的版本表达式会显示待确定条件，交由用户依据原安装说明选择。

`suggested` 是表单建议，`DECLARED` 表示读到了可解释声明；它们都不证明依赖已安装、镜像已构建或原目标已成功执行。保存时默认 Python 3.11 只有满足原硬性约束才可通过，平台不会用推荐信息绕过冲突。

## 2. 来源环境与运行组镜像

需要区分两种工件：

| 工件 | 包含内容 | 执行范围 |
|---|---|---|
| 目标解释器镜像 | 选定基础镜像、平台源码工具、Python 3.10 所需的 TOML 读取依赖 | 接收冻结源码并执行已有静态核对规则；不安装、导入原 Harness |
| 运行组镜像 | 冻结原源码、已核对候选与绑定、平台 worker、所选原依赖 | 实际加载原对象并执行运行组能力 |

准备目标解释器需要平台运行进程能够调用 Docker，并能连接可用的 Docker daemon。镜像构建需要的原镜像和包下载遵循实际网络条件，失败会保留实际返回状态。工具核对时在无网络的临时容器中传入冻结源码，返回结构化结果；不会把依赖安装或模型下载混入分析工具调用。

目标解释器的 `READY` 只说明源码工具镜像已准备。经过目标解释器核对的 Unit 在中央平台保留 `ENVIRONMENT_DEFERRED`／`MISSING`，需要匹配的真实运行组实例登记后才能调度；准备解释器本身不提供原库调用服务。

原生有限规则适用于受支持的解释器，并继续核对构造、原位调用及变换。解释器认识一种语法不等于平台已有对应规则，例如类型别名和类型参数作用域未覆盖时保留具体 `MISSING`，不因升级 Python 自动放开。

## 3. 前端操作

1. 在“配置 → Harness”接入原仓库，展开该来源的“运行环境”，查看“冻结仓库环境依据”和待确定条件。
2. 选择 Python、基础镜像、原依赖清单和原项目安装目录。可先“填写仓库建议”，再按原库说明调整；项目目录 `.` 表示源码根目录，子目录按原相对路径填写，留空则不安装项目。
3. 点击“保存并准备目标解释器”。等待状态从 `PREPARING` 变为 `READY`；`FAILED`、`BACKEND_UNAVAILABLE` 或 `NOT_PREPARED` 应根据原原因处理。
4. 新来源点击“分析”，由分析器发现入口、依赖与有限边界。已有完整候选则点击“按此环境重新核对已有候选”，生成零模型调用的 `ENVIRONMENT_RECHECK`，沿用原候选而重新执行源码及绑定核对。
5. 在“运行组与部署”选择实际运行所需的基础镜像、requirements、项目目录及额外 pip 需求，生成工件，再构建、发布并启动。这里选择的 Python 必须与源码核对的解释器一致；改变 Python 要先回到来源环境准备并重新核对。

“运行组与部署”的基础镜像字段会进入实际 Docker 构建，已不只是前端文本。构建过程核对镜像的实际 Python minor 和 patch 约束，按用户选择安装原清单、原项目和额外 pip 需求，执行 `pip check`，并记录依赖锁定清单。自定义 CUDA／系统依赖镜像需要已经具有与所选版本一致的 `python`；只填一个 CUDA 镜像名不保证原环境成立。

原项目安装可能按其原构建后端执行构建，这是实际运行镜像的安装步骤；源码证据发现和目标解释器工具不会执行这些原构建代码。Conda、系统包、自定义编译扩展或原 Dockerfile 中的额外准备工作，需要用户提供已按原要求准备的基础镜像。平台不会猜出或重写这套安装结构。

生成工件与镜像构建、发布、实例登记分别保存状态。K8S 沿用已生成清单中的 `IfNotPresent` 拉取策略：缺少目标镜像时由节点拉取已发布的镜像，不在任务执行中重新分析源码或现场猜依赖。目标节点仍需具备镜像仓库访问与原要求的 GPU／系统条件。部署后端与 Docker 工具配置见 [Docker 部署](Docker部署.md) 和 [运行组与 K8S](运行组与K8S部署.md)。

## 4. 修改、重新核对与已有资源

修改来源环境前，要结束正在进行的分析、原调用或研究运行，并排空、停止该来源的运行实例。正在构建或发布时也不能同时替换其环境。

保存新环境后，旧分析与实验记录继续保留，旧能力退出当前可调用状态，旧运行组工件不能作为新环境的就绪依据。环境重新核对不调用分析模型、不新增入口或拆分边界；若发现原候选缺入口、边界或当前规则不支持的结构，再由分析器补充或重新分析。

零模型重新核对不会删除命名 API 连接、凭据、权重登记、已放置权重或向量索引，也不会重算嵌入。这些资源继续按原依赖映射供实际运行环境使用，路径必须能在 worker 中访问。更换向量模型可能需要按原库要求重建索引；这与仅更换 Python 环境分别处理。环境准备、权重完整、向量服务可用和原目标调用成功仍是不同事实。

平台核对代码或来源环境身份变化后，旧目标解释器明确显示 `NOT_PREPARED`，需要重新准备。运行镜像还核对平台代码、源码、候选绑定及环境身份，旧版本 worker 不能直接冒充新工件。重启恢复的是历史和静态记录，不恢复旧原生会话；来源处于环境待核对状态时不会重新暴露旧 `READY`。

## 5. 实现与运行证据

主要代码为 `environments.py` 的机械发现和约束核对，`target_runtime.py` 的独立源码工具，`service.py` 的来源环境配置及零模型重新核对，`deployment.py`／`worker.py` 的环境冻结、构建和实际解释器核对；前端通过 `POST /api/harnesses/environment` 保存、准备或重新核对。

本次开发机只有 Python 3.11，完成了源码语法检查、独立 Python 进程的源码工具协议、生成环境工件与未应用 K8S 清单的核对、内存状态与隔离前端操作；没有运行 Docker daemon。跨 Python 版本的真实解释器镜像、服务器容器重建、GPU 原库依赖加载、K8S 拉取和原目标执行均为 `NOT_RUN`。现有历史实验结果保持原归因，本版代码更新不增加来源质量、部署成功或 RL 收益的结论。
