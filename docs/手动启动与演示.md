# 手动启动与使用

更新：2026-10-14，0.7.1。当前页面是普通 AI 对话，Harness 从用户填写的地址接入；原构造、内部调度及方案结果数据边由引擎绑定。

## 查看详情与摘除来源

左侧“来源与分析”“能力池”“任务详情”，或右侧“独立查看／查看完整详情”，会打开独立页面。来源与分析页显示全部分析历史、候选与检查报告；可按来源筛选。实时更新保留展开状态和滚动位置，不再每 1.5 秒收起列表。独立页面不会替换正在进行的对话。

来源卡片和配置列表中的“摘除来源”使其 Units 退出当前能力池。正在分析的来源停止后续模型请求；在途请求可返回并记录已产生的用量，但不会重新安装候选。未开始的原生调用被阻止，已经进入执行的调用允许返回；该方案的后续调用不会继续使用已摘除能力。

源码、分析与任务历史保留；“重新接入”复用最后完成的分析，以新绑定重新接入，不重复调用分析 API。有原调用尚在收尾时，页面提示结束后再接入。重启平台仍保留摘除状态，任务已保存的调用历史也继续显示。

摘除操作撤出能力池与调度，不删除源码／模型／数据，也没有自动调用未知的原生 `close` 或强行释放驻留模型；资源释放仍需原 Harness 明确支持的生命周期。

## 在本机启动

在仓库根目录启动。平台核心需要 Python 3.11 或以上，没有第三方 Python 依赖；URL 接入需要 Git。当前有限 B-CALL 原生构造宿主限定为用户确认的 Python 3.11，运行这类能力请使用 Python 3.11 环境。原 Harness 所需库安装在同一专属运行环境中。

Linux：

```bash
PYTHONPATH=src python -B -m seampact serve --home var/prototype --port 8880
```

Windows PowerShell：

```powershell
$env:PYTHONPATH = 'src'
python -B -m seampact serve --home var/prototype --port 8880
```

浏览器打开 http://127.0.0.1:8880。关闭运行终端中的程序使用 Ctrl+C。

现有私有模型配置可以通过 `--legacy-config` 复用，例如：

```bash
PYTHONPATH=src python -B -m seampact serve --home var/prototype --legacy-config var/demo/config --port 8880
```

这只读取已有接口配置，不复用旧的固定来源、能力包或任务宿主。Windows 保存的密钥需要在原 Windows 用户下使用；迁移到 Linux 后在页面重新填写密钥。

## 配置模型并对话

点击左侧“配置”，分别保存“对话模型”和“分析模型”。两者可以使用不同接口和型号。

| 配置项 | 填写方式 |
|---|---|
| 接口地址 | OpenAI 兼容基础地址；程序在其后追加 `/chat/completions`。本地常见形式为 `http://127.0.0.1:8000/v1` |
| 模型 ID | 填实际提供方或本地部署的模型 ID |
| API Key | 云端填写实际密钥；不要求密钥的本地对话接口可留空；保持地址不变时留空保留已有密钥 |
| 最大输出 token | 可选。填写实际模型支持的输出上限；留空采用可获取的模型能力或提供方默认值 |

分析接口使用云端 HTTPS。平台保留完整对话和分析工具上下文，不设置应用费用、调用次数或分析轮次上限；提供方本身的上下文和输出限制仍然存在。

保存对话模型后直接在首页发送消息。此时可以只有对话功能，不需要先接入任何 Harness。

## 接入 Harness

配置中填写仓库 URL 或本地目录。路径指运行平台的机器上的路径；Docker 内使用容器路径，例如 `/harnesses/my-harness`。

可选信息包括 Git 修订、已知原生入口和资源列表。入口用于说明要接入哪个完整 Harness，例如 `CorrectiveRAGWorkflow`；分析器仍可访问整个仓库，自行找构造、依赖和边界。资源填写 JSON 数组，例如：

```json
[
  {"path": "/harnesses/my-harness/config.json", "kind": "config"},
  {"path": "/harnesses/my-harness/data", "kind": "data"}
]
```

这些是用户已有的资源位置，不是预设拆分结果。模型／数据二进制保持为引用，不塞入分析上下文。

点击“接入 Harness”，来源出现在配置列表；再点击它的“分析”。后台真实调用分析模型：列目录、读源码、查构造／导入、提出入口和边界并接收引擎反馈。分析完成后，打开“运行状态”查看结果、实际输入／结果端口和能力池。同版本来源再次分析会保留已有模型上下文，并加入当前机械检查反馈，便于修正已发现的绑定缺口。

`READY` 表示入口、签名和声明的绑定已静态检查，初始化尚未运行。`SOURCE_BOUND` 表示源码入口／构造或原类型绑定有依据，不是完整语义证明。`MISSING` 显示未满足的依赖、资源、参数或接线条件；只有可调用入口会提供给对话模型。调用时才加载原 Harness、按声明执行原构造／初始化和入口，再返回实际结果。

业务输入由每次对话任务给出。需要初始化配置、模型目录等固定参数时，使用原默认值、原调用中的字面值或自己的实际配置；不要用示例文本／图片填满固定参数，把真正的任务接口变空。

## 在观察面板看什么

对话任务会显示最终回复或基础报错、总时延、实际 Unit 调用及各调用的等待／执行状态。上层调度显示选中的完整方案；下层调度安排原控制流已经使能的调用。能力池和任务执行使用同一个原生运行时。

当前方案步骤按声明顺序运行。后项参数可通过 `$result` 引用同一方案前项的真实结果；数据边、`after` 与声明顺序限制后继只能在前项成功后使能。原生对象留在本地方案 owner 内，普通数据结构在实际得到结果后核对。观察面板中的语义未决与绑定／执行状态分开。

MMCT、CRAG、NeMo、DiSP 的真实分析及已知资源缺口见[0.7 运行记录](0.7_规则兑现与实际运行.md)。尚未实现并行、跨入口驻留共享粒度和远程后端；当前界面中的多个 Unit 不表示多个独立容器。

服务器与 Docker 操作分别见[服务器部署](服务器部署.md)和[Docker 部署](Docker部署.md)。
