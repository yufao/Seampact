# 0.13.0 依赖镜像复用与统一构建

更新：2026-10-25。本文对应 0.13.0 工作区代码；平台安装与更新仍使用[服务器部署](服务器部署.md)中的统一入口。0.12.0 的接入功能和历史实验记录见[本地接入与实验接续](0.12_本地接入与实验接续.md)，不因版本更新改写其结果。

## 1. 本版变化

运行组构建改为 **基础镜像 → 第三方依赖镜像 → 原库源码与 worker**。原先整仓源码和平台核心代码位于依赖安装之前，源码变化容易使大依赖安装层失效；原构建还使用 `--no-cache-dir`，缺少跨构建的 pip 下载缓存。本版将可独立安装的依赖提前，并在同一 Docker builder 中使用 BuildKit 包缓存。

主要实现：

- `image_build.py` 从冻结的原依赖清单判断能否独立安装，生成两阶段 Dockerfile 和 `build-reuse.json`。
- `backends.py` 先导出命名依赖镜像，再构建包含原源码与 worker 的最终镜像，两步共用构建超时预算。
- `deployment.py` 在生成工件、构建、发布和启动之间核对当前来源安装身份、运行组契约及平台核心身份；过期工件要求重新生成。
- “运行组与部署”显示可复用依赖镜像名称。构建成功后，其他兼容来源可在基础镜像字段选择该引用。

本版不改变原库算法、原参数映射、拆分规则、W／H／R、owner 生命周期或 RL 学习器。

## 2. 统一复用规则

复用按运行环境输入判断，不按仓库名称、分析编号或来源接入时间判断。依赖镜像标识包括：

1. 用户选择的基础镜像引用和目标 Python。
2. 选中的原 requirements 文件路径、原始内容摘要，以及递归 `-r`／`-c` 引用的冻结文件。
3. 额外包索引和依赖阶段构建配方。

| 情况 | 处理 |
|---|---|
| 基础环境及完整依赖输入一致 | 生成相同的依赖镜像标识；同一 builder 中已有匹配缓存时复用安装层 |
| 仅原库源码、候选或平台核心改变 | 第三方依赖层可继续复用，重新构建源码、绑定与 worker 层 |
| 依赖清单不同，但已有依赖镜像满足该库要求 | 明确选择该镜像为基础，再按原清单和项目声明安装；pip 依据实际已安装版本处理 |
| 两个环境有相同下载包 | 同一 builder 中通过 pip HTTP／wheel 缓存减少重复下载；缓存不保证完全离线 |
| Python、系统库、PyTorch／CUDA 等要求不兼容 | 使用各自匹配的环境，不能为复用而放宽原声明 |
| 本地路径、可编辑安装或当前不能确定的 requirements 形式 | 保留原源码上下文与安装顺序，仍使用包下载缓存，不生成来源代码混入的共用依赖镜像 |

只有可确认的外部依赖清单才提前安装。原清单内容及 requirements → 原项目 → 额外 pip 需求的相对顺序不改写；额外 pip 需求和原项目安装属于来源层，不根据它们声称完整依赖镜像相同。构建仍执行 `pip check` 并保存 `environment.lock`。

依赖标识相同不等于已经命中缓存。实际复用还取决于基础镜像实际解析结果、builder、缓存是否仍在和包服务行为；运行身份以实际镜像 ID、冻结工件和依赖锁记录为准。下载缓存不进入最终 worker 镜像，也不代替凭据存储或模型权重登记。

GPU 可见性、驱动兼容和真实目标调用另行核对。镜像安装 PyTorch 的 CUDA 用户态运行库，不会替换宿主机驱动或宿主系统 Python；镜像、缓存与下载临时文件仍占用 Docker 所在磁盘。

## 3. 已接入来源更新到 0.13.0

先按[服务器部署](服务器部署.md)更新平台，确认 `/health` 返回 `{"status":"ok","version":"0.13.0"}`。已有来源沿用与新来源相同的构建流程：

1. 等待分析、原调用、训练及镜像构建结束，排空停止相关 worker。
2. 核对原来源、资源登记、连接、持久文件和当前环境选择。
3. 在该来源“运行环境”点击“保存并准备目标解释器”，准备与当前平台核心一致的检查环境。
4. 已有完整候选时点击“按此环境重新核对已有候选”，沿用候选生成零模型调用的重新核对记录。
5. 在“运行组与部署”填写来源已选环境，生成当前构建工件，再构建镜像。
6. 核对 worker 自己可见的权重、数据、凭据及 GPU 条件，使镜像对后端可达后启动实例，验证一次原目标调用。

| 已有内容 | 更新后的处理 |
|---|---|
| 原仓库和冻结源码 | 同机持久状态继续使用，不因构建机制更新重新克隆原仓库 |
| 已下载权重、数据和索引 | 继续保留，按 worker 实际挂载和原参数映射访问；不因重新核对而下载模型或重算索引 |
| 原分析候选 | 结构仍适用时零模型重新核对；确有候选或源码缺口时按正常修订流程处理 |
| 旧整库镜像 | 不会自动拆成新依赖镜像，也不直接充当新版 worker；按当前构建器重新生成和构建 |
| 旧下载内容 | 旧版未保留 pip 缓存的包不能保证复用，首次新构建可能重新下载；已有匹配基础镜像层仍由 Docker 正常复用 |

过期工件在构建、发布及启动前都会被拒绝，并提示重新生成；不为某次旧实验增加专用提取、转换或双轨构建路径。保存历史记录与继续运行旧执行环境分别处理。

## 4. 从前端复用已有依赖镜像

同一 daemon 上，先在成功构建的运行组中读取“可复用依赖镜像”名称。对另一个来源核对 Python、原库依赖和 GPU／系统要求，填写该名称作为基础镜像，仍选择该库自己的依赖清单和项目路径，然后准备解释器、重新核对候选并生成构建工件。

不能把另一库的整个 worker 镜像当作共用环境，以免带入来源源码、项目安装和绑定。生成器在依赖阶段只复制选中的依赖清单及引用文件，安装已确认可独立安装的第三方包，不复制原库源码、平台 worker、模型权重或运行凭据；所选基础镜像自身的内容仍须核对。跨 daemon／机器复用需要实际传输镜像或发布到双方可达的镜像仓库；同名标签不证明镜像已存在。

手动构建与前端使用同一份工件、`environment.json` 和 `build-reuse.json`；命令见[运行组远端操作](运行组远端操作.md)。本版构建缓存挂载需要 BuildKit，默认工具镜像提供 Docker CLI 与 buildx。

## 5. 存储和验证边界

模型权重和数据由持久目录／挂载决定位置；镜像、构建层和 BuildKit 包缓存由所用 Docker daemon 的数据目录决定。容器里的 `/data` 是平台挂载目标，不能据此推断它位于宿主机同名目录或大容量分区。平台对权重的挂载也不会自动传给独立 worker。路径核对见[Docker 说明](Docker部署.md)。

`df` 显示目录所在文件系统容量，不代替个人配额或管理员扩容策略确认。本版不修改磁盘挂载、系统驱动、系统 CUDA 或共享 Docker 配置，也不自动迁移、清理服务器镜像缓存。

已有一份原来源运行组镜像的真实构建成功记录，只能证明该次镜像构建与包依赖检查通过。0.13.0 的通用复用逻辑已做本地针对性核验，临时核验脚本与试构建目录已清理；开发机没有可用 Docker 引擎，**跨库实际缓存命中、节省时间和空间、GPU worker 推理及本轮完整调度训练仍须分别实测**。不能把旧构建成功或静态检查通过当作这些结果。

统一实现与临时核验文件清理规则见仓库 [AGENT.md](../AGENT.md)。本版不替换尚未完成适配和训练的集成示范，也不改写 0.12.0 及更早实验的数值与结论。
