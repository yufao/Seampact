# 镜像构建与依赖复用

更新：2026-10-31，当前工作区版本 0.14.8。本文统一维护平台、工具、检查解释器与 worker 的构建和复用规则。安装、接管、备份与更新仍从[服务器部署](服务器部署.md)进入；网络和挂载见[Docker 部署](Docker部署.md)，worker 启动与跨机操作见[运行组远端操作](运行组远端操作.md)。[0.13 记录](history/0.13_依赖镜像复用与统一构建.md)保留当时的功能起点、运行事实和验证边界。

## 1. 四类镜像分别做什么

| 镜像 | 内容与构建输入 | 复用边界 |
|---|---|---|
| 平台依赖环境 | 平台 Python 3.11 基础镜像、系统构建配方、`pyproject.toml` 的运行依赖、所选 extras 和构建依赖 | 不复制平台源码；依赖输入和基础镜像实际 ID 相同，核对已保存镜像与锁后复用 |
| 平台核心与工具 | 核心从已核验的依赖环境安装当前平台；工具层加入 Docker CLI 和 buildx | 平台源码更新只重建后续层；工具层继承同一平台，不安装 Harness 依赖 |
| 目标检查解释器 | 来源选定的 Python／基础镜像及检查器所需的平台模块 | 用于源码核对，不预装该 Harness 的完整运行依赖，也不证明原目标可执行 |
| 运行组依赖环境与 worker | 可独立安装的外部依赖在前；原项目、来源源码、绑定、所需平台模块及工件在后 | 依赖配方与已解析基础镜像 ID 决定环境镜像；最终 worker 使用已核验 ID 对应的构建引用 |

平台 `--extras rl` 只选择平台学习器依赖，不改变各 Harness 的 Python、PyTorch、CUDA 或原安装声明。权重、数据、凭据和运行状态使用各自持久目录或挂载，不进入共用依赖环境。从此前平台整库镜像首次切换时，需要建立一次新的独立环境，可能重新下载大包；旧镜像不会自动拆层导入。

## 2. 平台：首次解析一次，后续按锁和镜像身份复用

`deploy.sh` 与手动 Compose 共用 `deploy/build_platform.py`。环境身份只读取平台运行依赖、选中 extras、构建依赖和相关构建配方，结合基础镜像实际 ID、包索引及 PyTorch 选择；项目版本、描述、平台源码和 commit 不作为依赖环境输入。

首次没有保存记录时按声明解析依赖，保存全部已安装分发包的精确 `package==version` 锁、锁摘要、基础镜像 ID、依赖镜像 ID，以及实际 Python／PyTorch／CUDA 版本。后续更新先核对保存的实际镜像 ID、环境标签和锁；符合时直接复用。镜像被外部删除时按已保存锁重建，不重新按宽松范围选择新版本。索引或包文件不可达时仍可能失败；精确版本锁不等于已保存所有安装包，也不保证逐字节相同的下载产物。

平台核心 Dockerfile 要求传入 `DEPENDENCY_IMAGE`，只在该环境上离线执行 `pip install --no-deps --no-build-isolation`、`pip check` 和实际环境记录。更新源码不会触发平台依赖重新求解。不要跳过准备步骤直接构建 `deploy/Dockerfile`。

| 操作 | 结果 |
|---|---|
| 普通 `install`／`update`，已有相同环境记录 | 核验并复用；镜像缺失则按保存锁重建 |
| `--refresh-dependencies` | 明确重新解析依赖；保存此前实际锁与镜像记录，不表示自动更新宿主驱动 |
| `--dependency-lock <文件>` | 导入仅含精确 `package==version` 的完整环境锁；拒绝范围、URL、本地路径等形式 |
| `--base-image <引用>` | 先查本机镜像，缺失才拉取；同名远端标签变化不会自动刷新本机基础镜像 |
| `--pip-index-url`／`--pip-extra-index-url` | 选择平台依赖源，作为环境输入保存；URL 不带认证信息、查询参数或片段 |
| `--torch-version`／`--torch-index-url` | 所选 extra 必须声明 PyTorch；前者精确指定版本，后者指定 torch wheel 渠道 |

`deploy.sh` 持久保存依赖源、PyTorch 选择、基础镜像与 extras；导入锁复制到私有部署目录，后续不依赖临时原文件。刷新是本次命令的显式操作。首次 `--extras rl` 默认仍按仓库声明 `torch>=2.2` 解析；没有预设“推荐 CUDA 组合”。需要固定环境时，在首次构建显式选择精确版本与可用渠道，或导入已核实的完整锁。实际 CUDA 版本以构建记录为准，兼容性须另由目标机器和原调用核验。

保存 `deployment.json`、`platform-build.json`、`platform-environments/` 及导入锁。这些是私有部署材料，不写入 Git。只有精确锁且满足全部运行／构建依赖的环境才能重建；不从旧平台容器自动提取并冒充新的锁。`deploy.sh` 省略选项表示沿用已保存值，传空字符串（例如 `--torch-version '' --torch-index-url ''`）表示清空；移除 `rl` 时同时清空不再适用的 torch 选项。`--refresh-dependencies` 会取消之前导入锁的选择，按当前声明与版本／渠道选项重新解析，不能与本次 `--dependency-lock` 同用。

已核验的本地镜像 ID 会绑定到 `seampact-build-input:sha256-<完整 ID 的十六进制部分>`，再次核对映射后交给 BuildKit 的 `FROM`。这是同一镜像的本地标签，不复制依赖文件，也不是仓库 digest；实际 ID 仍保存在记录中。这样避免直接把 `sha256:<本地配置 ID>` 写进 `FROM` 的兼容性问题，见 [BuildKit 上游记录](https://github.com/moby/buildkit/issues/2204)。不手动改指这些标签，构建和 Compose 使用同一 daemon 的默认 builder。

### 手动构建平台与工具镜像

在所选源码目录执行；状态目录放在私有部署工作区。`--image` 同时构建最终核心镜像，省略时只准备依赖环境：

```bash
cd "$SEAMPACT_CODE_DIR"
SEAMPACT_REVISION="$(git rev-parse HEAD)"
SEAMPACT_CORE_IMAGE="seampact-core:local"
SEAMPACT_TOOLS_IMAGE="seampact-tools:local"
python3 deploy/build_platform.py \
  --state-dir "$HOME/seampact-workspace/platform-environments" \
  --extras rl --revision "$SEAMPACT_REVISION" \
  --image "$SEAMPACT_CORE_IMAGE"
docker buildx build --load --builder default -f deploy/Dockerfile.tools \
  --build-arg "PLATFORM_IMAGE=$SEAMPACT_CORE_IMAGE" \
  -t "$SEAMPACT_TOOLS_IMAGE" .
```

不需要神经学习器时省略 `--extras rl`。后续每次调用继续使用同一 `--state-dir` 和已选依赖选项；手动辅助程序不会读取 `deploy.sh` 的部署配置。使用同一 Docker daemon 和默认 Docker builder，使本机镜像 ID 对最终构建可见；切换远端 builder 不保证能读取这些本机镜像。

### 手动 Compose

保留原项目名、私有配置、文件组合和挂载。先使用同一辅助程序生成构建环境文件，再让 Compose 构建；以下为基础平台示例，既有部署沿用原服务管理方式：

```bash
cd "$SEAMPACT_CODE_DIR"
SEAMPACT_COMPOSE_BUILD_ENV="$HOME/seampact-workspace/platform-build.env"
python3 deploy/build_platform.py \
  --state-dir "$HOME/seampact-workspace/platform-environments" \
  --extras rl --revision "$(git rev-parse HEAD)" \
  --compose-env "$SEAMPACT_COMPOSE_BUILD_ENV"
BUILDX_BUILDER=default docker compose --env-file "$SEAMPACT_COMPOSE_BUILD_ENV" \
  -f deploy/compose.yaml build
docker compose --env-file "$SEAMPACT_COMPOSE_BUILD_ENV" \
  -f deploy/compose.yaml up -d --no-build
```

生成文件包含 `SEAMPACT_DEPENDENCY_IMAGE` 的已核验本地构建引用、`SEAMPACT_EXTRAS`、版本和修订。已有 Compose 私有环境文件继续传入，多个 `--env-file` 时把本次生成文件放最后；shell 中同名变量也须与生成结果一致。工具 Compose 仍须先按上文构建核心和工具镜像，选择工具镜像后用原完整文件组合 `up --no-build`；不要让 Compose 另行在线安装平台依赖。手动 Compose 的网络、用户、socket 和挂载条件见[Docker 部署](Docker部署.md)。

## 3. 运行组：只提前安装已确认不需要源码的依赖

所有来源经过同一个工件生成器，按原 `requirements → project → packages` 顺序执行；不合并或放宽原声明，不从外部包装替代分析器的自动接入。

| 原安装内容 | 所在阶段与原因 |
|---|---|
| 已确认全部为外部依赖的 requirements 及递归 `-r`／`-c` 引用 | 前置依赖环境；复制冻结清单和引用文件 |
| 本地路径、可编辑安装或无法确认独立性的清单 | 来源阶段；保留源码上下文和具体原因 |
| 原项目安装，包括动态生成依赖的项目 | 来源阶段；项目安装可能读取源码，不推断其完整依赖等价 |
| 静态外部额外包，且前序安装都可在源码之前完成 | 前置依赖环境；顺序保持 |
| 存在前序来源清单／项目安装，或额外包本身需要源码 | 来源阶段；不为复用改变安装顺序 |

`build-reuse.json` 保存前置／后置安装计划、原因与依赖配方摘要。后端解析基础镜像实际 ID，核对依赖环境的配方及基础镜像标签；同名标签本身不证明兼容。成功复用后，最终 worker 从核验过的环境 ID 对应的本地引用构建。来源源码、绑定、运行组契约或相关 worker 实现改变会重建后续层，但在前置输入不变时可以复用依赖环境。最终执行 `pip check` 并保存 `environment.lock`；该 worker 记录反映实际安装，不等于平台辅助程序的自动精确锁重建机制。

BuildKit pip 下载缓存减少仍需执行安装时的重复下载，与直接复用整个已安装环境分别判断。缓存属于所用 builder，不进入最终 worker 镜像；驱逐后按正常声明安装。跨 daemon／机器复用需要实际传输镜像或使用双方可达仓库，不能仅复制标签。前端分别显示待核验、已构建、已复用和失败状态，以及实际环境 ID 和前后置原因；`observed_cache_hit=NOT_CHECKED` 仍表示没有解析下载缓存命中情况。生成候选环境名不算已构建。

手动操作使用工件内的 `seampact.backends` 入口，执行与前端相同的基础镜像解析、环境核验／构建和最终镜像构建，不再维护另一套固定两条 `docker build`。具体命令见[运行组远端操作](运行组远端操作.md#读取构建输入并构建)。Docker 不可用时页面返回的原始命令只执行完整分阶段构建，不声称已经核验或复用命名环境。

## 4. 检查、运行身份与已有来源

检查解释器和 worker 分别按各自所需平台模块的保守导入闭包计算实现身份。与其无关的服务／训练代码变化不必让目标工件失效；相关共享模块或闭包变化仍会失效。只打包身份覆盖的模块，研究运行保存的完整平台源码归档继续保留，不用较小执行包替代完整研究出处。

来源安装身份、运行组契约、目标环境和相关平台实现仍在生成、构建、发布及启动时核对。需要更新时，先等现有工作结束并排空释放 worker，核对资源与环境，在来源点击“保存并准备目标解释器”，对完整候选点击“按此环境重新核对已有候选”，再生成并构建当前工件、使镜像可达、启动和验证原目标。原仓库、冻结源码、持久权重、数据和历史结果保留，旧整库镜像不自动拆成共用环境。本次身份格式变化需要按同一流程重生成旧工件；之后仅相关执行模块变化才使对应身份失效。

### 一键准备与普通重启

来源“运行环境”和具体运行组卡片提供“一键准备并启动”。它读取已保存环境，串行调用准备解释器、零模型重检、生成工件、构建、发布、启动和预热接口；跳过仍有效阶段，不调用分析模型或猜测缺失配置。多运行组来源须在具体组卡片操作。失败后显示当前步骤，修正条件再点击继续；保持页面打开，关闭页面会停止后续串联，已提交后台构建继续保留。

普通重启只改变 session；相关代码、环境、契约和安装身份未变且镜像仍存在时，不重复准备解释器、重检或构建。旧会话实例仍须实际释放，再创建新实例并按契约预热。UNKNOWN 的释放须由用户明确选择，未决调用保留原状态；外部删除的镜像按正常构建补齐。代次代表新进程实例，防止旧响应混入并记录加载、驻留与调用成本，不复活原模型对象。

终态卡片的“清理记录”和组级“清理已释放记录”，只移除已停止／失败且实际释放、无任务占用及未决调用的面板历史。原实例、事件和研究成本证据保留，代次继续递增；不删除镜像、权重或运行中的容器。

## 5. 证据与存储边界

镜像、构建层和 pip 缓存由实际 daemon／builder 存储决定；平台 `/data` 与 worker 权重挂载分别核对，详见[Docker 路径说明](Docker部署.md#4-数据源码和资源的路径视角)。CUDA 用户态库安装在镜像里，不替换宿主驱动。环境镜像可复用不证明 GPU 可见、权重可读或原目标成功。

2026-10-29 本地完整检查 **144 项通过**，包含依赖选择、按锁恢复、实际镜像身份核对、安装顺序和执行闭包检查；Docker 调用使用命令模拟，开发环境没有可用 Docker daemon。真实 Linux 构建、跨来源缓存命中、重建耗时／空间节省、GPU worker 推理和 K8S 运行仍为 **NOT_RUN**。0.13 曾有单来源镜像真实构建成功记录，该历史事实不扩展为本轮新机制的真实运行结果。没有用静态通过或镜像名称推断实际缓存收益，也没有改写原实验数值、失败分母和出处。
