# 服务器部署：首次安装与更新

更新：2026-10-25，当前版本 **0.13.0**；以下统一脚本适用于 0.11.1 起的 Linux Docker 平台。日常只有两个入口：`bash deploy.sh install` 首次部署，`bash deploy.sh update` 更新已有部署。后续版本继续使用这两个命令；镜像标签、构建参数和替换步骤由仓库中的脚本维护。

命令在服务器的宿主终端执行。平台在容器内运行，默认工具镜像包含 Docker CLI 和 buildx，通过本机 Unix socket 使用服务器已有的 Docker daemon；不在平台容器中另起 daemon。容器内的 Python 仍为 3.11，Harness 的独立解释器和运行组按网页选择的环境构建。

本页是平台安装与更新的主入口。[Docker 网络与工具](Docker部署.md)解释网络和路径；[运行组远端操作](运行组远端操作.md)处理 worker；[运行组与 K8S](运行组与K8S部署.md)保留研究机制和 K8S 专题。版本功能与历史运行事实见[当前实现](当前实现.md)，不再按版本复制部署步骤。

## 本次更新到 0.13.0

确认待部署代码已提交并上传至所选远端，待分析、任务、训练和 worker 收尾后，在已有部署的源码目录执行：

```bash
bash ./deploy.sh update
```

若此前使用轻量平台、现在要运行三种学习器，则执行 `bash ./deploy.sh update --extras rl`；已有 `rl` 构建选项会自动沿用。自定义部署根目录时仍加原来的 `--root`，尚无部署记录的旧平台按第 3 节接管，不把已有数据当首次空目录安装。

更新后从实际访问的平台地址打开 `/health`，应返回 `{"status":"ok","version":"0.13.0"}`。仍显示旧版本时，核对实际容器和 Git 版本；单独刷新浏览器不会升级后端。

本版更新运行组依赖镜像与统一构建流程。平台更新后，已有来源先准备与当前核心一致的目标解释器，再对完整候选做零模型重新核对，生成当前构建工件并构建镜像。原仓库、持久权重与数据继续使用；旧整库镜像不会自动拆成依赖镜像，旧版未保留的 pip 下载缓存也不保证可复用，首次新构建可能重新下载依赖。具体规则见[0.13.0 更新说明](0.13_依赖镜像复用与统一构建.md)。

先验证服务在线和一次原目标调用，再开始短路径对照与训练。升级不会启动外部模型服务，也不续跑此前已中断的训练；本版功能和已知实验状态见[0.13.0 更新说明](0.13_依赖镜像复用与统一构建.md)。

## 1. 执行前提

服务器已有 Bash、Python 3、Git、Docker CLI 和当前账号可访问的本机 Docker 服务。脚本不安装系统软件，不修改共享服务器的 Docker 权限或 context。选定 daemon 后，后续操作使用保存的同一 Unix socket，不会因新终端切换 context 而误操作另一套服务。

```bash
command -v bash python3 git docker
docker version
docker context show
```

使用个人 rootless Docker、服务尚未运行时，按已有安装情况执行：

```bash
systemctl --user start docker
docker context use rootless
docker version
```

执行安装或更新期间不在网页提交新分析、任务或训练。更新前先等待现有工作收尾，在“运行组与部署”排空停止并释放旧实例；脚本发现运行／排队的工作或尚未释放的 worker 会停止更新，不替使用者中断研究运行。K8S 中的平台沿用 K8S 专题操作，本脚本管理本机 Docker 平台。

## 2. 首次部署：服务器还没有代码仓库

从同一待部署版本取得仓库根目录的 **`deploy.sh` 单个文件**，用 SFTP 上传到服务器自己的家目录。脚本可独立执行，不要求先有 Git 克隆。仓库 URL 使用目标机器已有的 Git 授权，不在 URL 中附带 token 或密码。

```bash
read -r -p '仓库 URL（不含凭据）: ' SEAMPACT_REPO_URL
bash "$HOME/deploy.sh" install --repo "$SEAMPACT_REPO_URL"
```

默认工作区为 `~/seampact-workspace`：

| 路径 | 内容及保留方式 |
|---|---|
| `Seampact/` | Git 源码；更新只快进拉取，不自动丢弃本地修改 |
| `data/` → 容器 `/data` | 配置、凭据、分析与任务记录、状态库、冻结源码、策略及导出包 |
| `harnesses/` → 容器 `/harnesses` | 自己放置的来源、数据及权重；更新沿用原挂载 |
| `deployment.json` | 私有部署记录：容器、daemon、构建选项、镜像归属等 |
| `backups/` | 更新前停机复制的完整 `/data`，以及私有容器配置 |

已有 Git 克隆、还没启动过平台时，直接使用该克隆：

```bash
git -C /path/to/Seampact pull --ff-only
bash /path/to/Seampact/deploy.sh install --code-dir /path/to/Seampact
```

`install` 在目录不存在时克隆源码，但不会替已有克隆执行 `git pull`；使用上面的手动快进更新后再安装。`update` 默认先快进拉取，`--local` 才跳过拉取。构建开始时核对脚本打印的版本，当前应为 `0.13.0`。

自定义工作区、端口并安装三学习器所需依赖时：

```bash
bash "$HOME/deploy.sh" install --repo "$SEAMPACT_REPO_URL" \
  --root "$HOME/seampact-workspace" --port 8880 --extras rl
```

`--extras rl` 安装学习器依赖，默认空值为轻量平台。只有不需要网页准备解释器、构建或管理 Docker worker 时，才在首次安装加 `--without-tools`。其他首次配置包括 `--container`、`--data-dir`、`--harness-dir`、`--network`；完整参数执行 `bash deploy.sh --help`。配置被保存，日常更新不用重新填写；自定义 `--root` 后，每次仍使用该工作区。

首次安装拒绝已有同名容器或非空状态目录；原容器仍存在时按下一节接管，原容器已删除时明确使用下述 `--reuse-data`，避免无意创建空平台。

## 3. 更新：服务器已经部署过旧版本

### 已经由本脚本管理

```bash
bash "$HOME/seampact-workspace/Seampact/deploy.sh" update
```

自定义工作区时继续加 `--root /path/to/workspace`。脚本读取保存的容器和构建选项，在当前分支执行 `git pull --ff-only`，然后重新进入拉取后的脚本。更新命令无需填写版本号。代码须已提交并上传到所选 Git 远端；本机未推送的变化不会出现在服务器。

`--local` 用于已由自己更新好的干净 checkout，只跳过 `git pull`，仍执行构建、备份和容器替换。它不允许忽略本地修改，也不表示直接重启旧镜像。

### 旧版本通过 docker run 启动，尚无部署记录

取得新版本的单独 `deploy.sh`。填写原平台的**准确容器名**和已有代码目录：

```bash
read -r -p '原平台容器名: ' SEAMPACT_OLD_CONTAINER
bash "$HOME/deploy.sh" update \
  --container "$SEAMPACT_OLD_CONTAINER" \
  --code-dir "$HOME/seampact-workspace/Seampact"
```

脚本读取原配置，保留 bind／命名卷／匿名卷的实际身份、读写属性、环境变量、容器用户、补充组、端口、网络、启动命令和资源配置。原来使用 host 网络时继续保留，不自动改成 bridge。已有状态目录无需改名或搬到新默认目录。

旧平台没有 Docker 客户端和 socket、现在需要网页操作 Docker 时，在**这一次更新**加 `--with-tools`。它构建工具镜像并挂载当前选定 daemon 的 socket；若原挂载指向另一 daemon，会先报错，不替换原挂载。后续沿用同一构建配置。若服务器连代码克隆也已不存在，可提供 `--repo` 重新拉取；原数据仍以原容器挂载为准。

### 原容器和镜像已删除，旧数据目录还在

先确认当前及其他运行位置没有进程写入该状态目录。对本机选定 daemon，脚本会额外检查可写挂载是否重叠。明确指定旧数据目录，用 `install --reuse-data` 重建平台，例如旧指南默认的数据目录为 `seampact-data`：

```bash
bash ./deploy.sh install --reuse-data \
  --code-dir "$PWD" \
  --container "seampact-platform-$(id -u)" \
  --data-dir "$HOME/seampact-workspace/seampact-data" \
  --harness-dir "$HOME/seampact-workspace/harnesses" \
  --with-tools --extras rl
```

`--reuse-data` 仅用于 `install`，必须提供已有的 `--data-dir`，其中须存在 `platform.sqlite3`。脚本先构建镜像、创建保持停止的新容器，再从该容器的 `/data` 挂载复制完整停机备份，成功后才启动原目录。不会清空、迁移或用新目录覆盖旧数据；备份包括数据库、WAL、配置和目录内其他文件。`--extras rl` 对应需要学习器的部署，可按原用途选择。

原容器已删除后，Docker 不能再提供它的旧端口、环境变量、网络或额外挂载；此路径使用新平台的 bridge 网络和默认端口，需要的自定义配置须依据原记录补齐。目录外的权重、来源和环境变量凭据也不因数据库文件仍在而自动恢复。旧数据是否完整、实际任务是否可运行仍须以恢复后的结果为准。完成后使用普通 `update`，不重复执行恢复安装。

### 旧版本通过 Compose 启动

首次接管需要明确把平台后续管理交给本脚本：

```bash
bash "$HOME/deploy.sh" update \
  --container "$SEAMPACT_OLD_CONTAINER" \
  --code-dir "$HOME/seampact-workspace/Seampact" --adopt-compose
```

接管保留原容器配置和网络，仅移除平台容器的 Compose 管理标签。此后统一用 `deploy.sh update`；不要再对旧 Compose 项目执行 `up` 来重建该平台。原项目其他服务、网络与卷保留。若继续由 Compose 管理，则保留原私有环境文件和同一项目，按[Docker 说明](Docker部署.md)处理，不混用两个管理入口。

`--rm`、共享其他容器命名空间／卷、links 等不能直接接管的情况，会在停止原容器前报出原因。平台须使用标准启动入口和 `--home /data`，且 `/data` 有可写的持久挂载；只存在于容器可写层的数据，须先完整迁出并显式挂载，再接管。

## 4. 更新顺序与数据保留

1. 核对部署记录、原容器及挂载；检查 Git 工作区，再快进拉取。
2. 按实际版本、commit 和本次构建标识构建核心镜像；需要工具时再构建工具镜像。原平台此时仍在运行。
3. 核对工作已收尾，创建尚未启动的新容器，检查 Docker 是否接受原配置。
4. 停止原平台，将完整 `/data` 复制到新的私有备份目录，再让新容器使用原数据挂载启动。
5. 新容器 `/health` 返回预期版本，所需 Docker 工具可用后，才删除原平台容器，清理符合条件的旧平台镜像。

删除旧容器不带 `-v`。配置、历史结果、冻结来源、模型和权重继续位于原持久挂载中。原来临时在容器内安装的依赖或写到未挂载路径的内容不会自动进入新镜像；依赖应进入构建声明，持久文件应进入挂载目录。

备份复制的是**已停止平台的整个 `/data`**，包含 SQLite 及其 WAL／辅助文件、配置、策略和部署材料，不在运行中单拷 `.sqlite3`。外部 Harness、数据与权重保留原挂载，不默认重复备份大模型。备份文件由运行脚本的宿主账号拥有；恢复时按原容器 UID/GID 和挂载方式核对拥有者。[Docker cp](https://docs.docker.com/reference/cli/docker/container/cp/)

备份可能包含凭据，只保存在私有工作区，不进 Git，也不把 `deployment.json` 或 `container.json` 全量贴到聊天。原配置和数据挂载仍保留，因此不要把旧容器或 `docker commit` 镜像当成数据备份。

构建失败时原平台继续运行。替换途中或新版本启动失败时，脚本保留原容器、镜像、数据挂载和已完成的备份，停止继续更新；若新容器已经写入状态，先恢复停机备份再考虑运行旧版本，不直接拿旧镜像读取可能已变化的状态。脚本不自动执行数据回滚。

平台重启会更换 session，保留历史不等于恢复内存中的模型对象或在途调用。更新后从网页启动新 worker 实例；平台核心、协议或安装身份变化时重新生成运行包、构建 worker 镜像，见[运行组远端操作](运行组远端操作.md)。

## 5. 旧容器和镜像的清理范围

| 对象 | 脚本处理 |
|---|---|
| 本次被替换的原平台容器 | 新平台报告预期版本后删除；失败时保留 |
| 本脚本构建的核心／工具镜像 | 保留最近两次成功部署，仅删除更旧、归属本部署且无容器引用的标签 |
| 接管前已有的镜像 | 保留；仅凭名称或旧版本号不能判定归属 |
| worker、目标 Python、CUDA／模型基础镜像 | 保留，由运行组生命周期与实际用途决定 |
| 宿主数据、权重、Docker 卷、网络 | 保留 |
| 状态备份、Docker 构建缓存 | 保留，不纳入每次更新自动清理 |

重复执行定向镜像清理：

```bash
bash "$HOME/seampact-workspace/Seampact/deploy.sh" cleanup
```

不执行全局 prune，不强制删镜像，不按 `seampact-*` 名称批量删容器。未引用不表示没有研究价值，尤其 worker 重建可能涉及原依赖和 CUDA。接管前的旧镜像需手动核对准确 ID 和全部容器引用，再用不带 `-f` 的 `docker image rm`；删除一个标签不一定释放多标签镜像的层，见 [Docker image rm](https://docs.docker.com/reference/cli/docker/image/rm/)。

## 6. 手动命令与报错处理

显示概要；不打印完整环境变量或私有容器配置：

```bash
bash "$HOME/seampact-workspace/Seampact/deploy.sh" status
docker logs --tail 80 seampact-platform
```

捕获到的命令／Docker API 失败详情保存在工作区的私有 `last-error.txt`，终端只提示位置；构建进度直接显示在终端。本地查看该文件可得到原始错误，不将其中的凭据、路径或容器配置整体分享。

**rootless 启动时报 `setgroups: invalid argument`：** 2026-10-25 修正了工具 socket 附加组的设置：容器 root 已映射 daemon 用户时，不再追加宿主数字 GID；普通 Docker 保留按 socket GID 添加组。旧失败容器仍保留创建时的配置，单独更新源码或再次 `docker start` 不会重写它的 `GroupAdd`。先核对 `User`、`GroupAdd`、socket UID/GID 和 rootless 映射；若是从未启动的首次安装，须验证记录中的容器 ID、Created／未运行状态、`/data` 原挂载及完整停机备份后，移除该失败容器（不加 `-v`），保存原部署记录，再解除仅对应此次初次安装的 pending 并使用修复后的脚本恢复安装。已有旧平台的中断更新不适用该处理，仍按下文备份与回滚路径核对。此修正已完成本地构造核验，服务器启动结果待实际返回。

对上述已经核对的“首次安装、Created、从未启动、已有完整备份”情况，可在拉取修复后的干净源码后执行：

```bash
python3 deploy/recover_created.py --root "$HOME/seampact-workspace"
```

此工具使用现有部署锁，仅处理记录中的同一容器 ID；核对原数据挂载和备份后，先保存部署记录副本，再移除未启动容器并解除该次 pending。它不删除卷、镜像、数据或备份，不处理已有旧平台的中断替换，不启动新容器。任一身份或状态不符会停止。随后按第 3 节 `install --reuse-data` 使用同一数据目录重新安装。

已接管的部署使用原容器名。以下对应脚本内主要操作；手动替换前仍须保存原配置和挂载，不照新部署默认值覆盖旧部署。

| 环节 | 对应命令／动作 | 报错后处理 |
|---|---|---|
| 更新代码 | `git -C "$SEAMPACT_CODE_DIR" status --short`、`git -C "$SEAMPACT_CODE_DIR" pull --ff-only` | 先处理本地修改或分支分叉，不自动 reset／stash |
| 确认版本 | `git -C "$SEAMPACT_CODE_DIR" rev-parse HEAD` | 确认选定分支已包含需要部署的代码 |
| 构建镜像 | 下方完整命令 | 核对基础镜像、依赖和实际错误，构建完成前不停止旧平台 |
| 停止原平台 | `docker stop "$SEAMPACT_PLATFORM_NAME"` | 先等任务收尾并在网页排空释放 worker |
| 备份状态 | `docker cp "$SEAMPACT_PLATFORM_NAME:/data/." "$SEAMPACT_BACKUP_DIR/data"` | 先创建备份父目录、保持原平台停止；核对空间和权限 |
| 查看新平台 | `/health` 及 `docker logs` | 版本或启动不符时保留原容器、镜像和备份 |
| 检查工具 | `docker exec "$SEAMPACT_PLATFORM_NAME" docker version`、`docker exec "$SEAMPACT_PLATFORM_NAME" docker buildx version` | 无 CLI 用 `--with-tools`；权限问题检查 socket、容器用户与补充组 |
| 删旧平台容器 | `docker rm "$SEAMPACT_OLD_CONTAINER"` | 确认是已替换且停止的那一个，不加 `-v` |

手动构建核心与工具镜像，在干净源码目录执行：

```bash
cd "$SEAMPACT_CODE_DIR"
SEAMPACT_REVISION="$(git rev-parse HEAD)"
SEAMPACT_VERSION="$(python3 -c 'import pathlib,re; print(re.search(r"^version\s*=\s*\"([^\"]+)\"", pathlib.Path("pyproject.toml").read_text(), re.M).group(1))')"
SEAMPACT_CORE_IMAGE="seampact-core:$SEAMPACT_VERSION-${SEAMPACT_REVISION:0:12}"
SEAMPACT_TOOLS_IMAGE="$SEAMPACT_CORE_IMAGE-tools"
docker build -f deploy/Dockerfile \
  --build-arg "SEAMPACT_VERSION=$SEAMPACT_VERSION" \
  --build-arg "SEAMPACT_REVISION=$SEAMPACT_REVISION" \
  --build-arg "SEAMPACT_EXTRAS=${SEAMPACT_EXTRAS:-}" \
  -t "$SEAMPACT_CORE_IMAGE" .
docker build -f deploy/Dockerfile.tools \
  --build-arg "PLATFORM_IMAGE=$SEAMPACT_CORE_IMAGE" \
  -t "$SEAMPACT_TOOLS_IMAGE" .
```

容器创建、停机、改名、启动和移除对应 Docker Engine API 的 `containers/create`、`stop`、`rename`、`start`、`DELETE ...?v=0`。使用 API 是为了按原 JSON 保留配置，不需要将原凭据拼成 shell 参数。

处理中断的替换：先用 `status` 找保留容器和最新备份，查看本地容器日志。确认新旧平台均停止后，先将当前数据完整保存为另一份副本，再把停机备份恢复到**原挂载位置**，最后才启动对应原镜像／保留容器。bind 和命名卷的恢复目标不同，不套用同一删除／复制命令。处理后核对私有记录的 `pending`、当前容器和镜像字段；不要仅删 `pending` 来忽略未解决的状态或容器。

## 7. 打开网页与配置资源

默认平台发布服务器回环 `127.0.0.1:8880`。在自己的电脑建立 SSH 本地转发：

```bash
ssh -N -T -o ExitOnForwardFailure=yes \
  -L 127.0.0.1:18880:127.0.0.1:8880 "$SEAMPACT_SSH_TARGET"
```

`SEAMPACT_SSH_TARGET` 使用自己的 SSH 配置名或登录目标，不写进仓库。保持终端连接，在电脑打开 http://127.0.0.1:18880。服务器端口变化后同步修改转发目标。

模型角色、命名服务、权重及依赖绑定见[资源配置操作](资源配置操作.md)。路径填写执行容器可见的 `/data`、`/harnesses` 或其他保留挂载；worker 的挂载 source 则由 daemon 按宿主路径解析，见 [Docker bind mounts](https://docs.docker.com/engine/storage/bind-mounts/)。Windows DPAPI 凭据不能直接作为 Linux 凭据迁移。

本版没有执行远端更新、Docker 镜像构建、GPU 或 K8S 运行；脚本及模板交付不改变已有研究结果与 `NOT_RUN` 边界。
