# 实验镜像保留与备份改进计划

2026-11-03，二次审查设计。后续代码已在本地按本方案接入，操作、实测记录及实际限制见[实验镜像保留与备份](../部署与操作/实验镜像保留与备份.md)。本地已完成真实 worker 同 ID 重启、归档恢复、VOLUME 覆盖及引用丢失中止检查；本页其余设计核验项不能据此一并视为通过。

## 1. 目标与推荐选择

平台协调容器在实验期间持续运行。真实 worker 继续按现有规则排空、停止、删除，确认后端容器消失后归还运行组。调度器在同一轮内可以多次释放并重新启动 worker。

推荐在实验准备阶段，由平台为本轮每张最终运行镜像创建一个独立的、始终处于 `created` 状态的引用容器。本轮全部结束后删除这些引用容器。镜像备份由操作者按需选择，供下一轮准备时恢复。正式运行期间只启动已冻结且本机可用的镜像，镜像缺失即中止本轮并记录准备条件失败。

这里的“本轮”是一次冻结的实验范围，可以包含多个策略臂、多个调度窗口和重复。它从统一准备开始，到最后一个臂结束、请求排空、运行资源释放及必要结果持久化后结束。单个任务完成、单个窗口结束或一个 worker 缩容，都不能结束镜像保留。

镜像保留范围只管理工件寿命，使用独立 `retention_scope_id` 关联已有实验运行 ID。它不改变实验协议中的统计比较单位。准备清单须事先列明哪些子运行组成一个完整比较单元，例如同一工作负载与种子下的原生／平台配对。后面某个单元中断时，先前已经完整结束且条件有效的单元仍可保留使用，中断单元不得拼接新范围的结果冒充一次完整配对。尚未完成的同一训练运行仍按第 5 节处理。

### 方案比较

| 方案 | 同轮释放 worker 后再次启动 | 跨轮恢复 | 成本与边界 | 选择 |
| --- | --- | --- | --- | --- |
| 每轮独立引用容器 | 引用有效期间可用同一镜像 ID 启动 | 本轮收尾后依赖本机镜像是否仍存在 | 新增少量容器元数据和可写层，维持镜像磁盘占用，无模型进程 | 必选主方案 |
| 仅导出备份 | 镜像仍可能被清理，需重新导入才可启动 | 可导入已保存镜像并核对原 ID | 占归档空间及导入时间 | 单独使用不满足同轮要求 |
| 引用容器加选定备份 | 同轮使用引用保留 | 下一轮优先从备份恢复 | 归档与导入安排在计量窗口之外 | 推荐组合 |
| 既有镜像仓库中的冻结工件 | 单独使用仍可能在中途发生拉取 | 依靠可访问的镜像仓库恢复 | 需要传输和仓库存储 | 有现成仓库时可替代归档，仍配引用容器 |
| 缺失后重新构建 | 同轮身份和准备成本可能变化 | 可生成下一轮工件 | 可能重新安装或下载依赖 | 仅用于下一轮准备且无可用副本时 |

`docker create` 建立容器和镜像的引用而不启动进程。普通 `docker image prune -a` 针对无容器引用的镜像，因此引用容器适用于当前已确认的未引用镜像回收场景。保护边界见第 7 节。[Docker create](https://docs.docker.com/reference/cli/docker/container/create/) · [Docker image prune](https://docs.docker.com/reference/cli/docker/image/prune/)

## 2. 仓库审查发现

| 现状及代码入口 | 设计缺口 | 改进要求 |
| --- | --- | --- |
| `hosting/backends.py` 的 `stop()` 执行容器 stop 和 rm，`hosting/deployment.py` 的 `_advance_stop()` 据结果结算释放 | 运行容器删除后，实验仍需使用的镜像没有独立持有者 | 在实验层新增引用持有，延续真实 worker 的现有释放条件 |
| `scheduling/joint.py` 的 `Window._teardown()` 会在窗口末释放运行实例 | 把引用清理放在同一处会过早解除保护 | 引用覆盖外层整轮，内层窗口只释放真实实例 |
| `scheduling/training.py` 的 `_run()` 包含窗口循环、结果保存及最终收尾 | 单个调度运行与原生／平台配对的人工分段还没有统一镜像保留范围 | 使用轻量实验范围记录覆盖子运行，普通单次运行使用自身范围 |
| `_start_gap()` 主要核对工件及发布记录，普通 Docker worker 启动尚未显式使用 `--pull=never` | 历史 BUILT／NOT_REQUIRED 与本机镜像实时可用性混在一起，启动仍有隐式拉取入口 | 运行前核对冻结 ID 与引用，Docker 创建和启动路径强制禁止拉取 |
| `hosting/managed_services.py` 已用冻结 ID 和 `--pull=never` 启动本地服务 | 仅持有 worker 镜像会漏掉稍后也会缩容／重启的本地服务 | 运行清单包含本轮受管服务依赖闭包 |
| `target_runtime.py` 用独立检查解释器镜像执行分析核验 | 工件准备与实验执行容易混淆 | 需要的分析核验在准备阶段完成，实验重启已有 worker 不依赖重新运行分析器 |
| `joint.py` 已区分观察阶段、初始化就绪和实际调用，通用失败仍可能被纳入资源动作失败 | 镜像缺失可能被记成模型加载失败，污染时延、学习反馈和有效窗口 | 增加准备条件失败类别，保留已发生成本，终止后续运行 |
| 原生 CLI 可以在同一 worker 内每次启动模型子进程 | worker 存活不能证明原模型驻留 | 暖态依据原模型／服务已就绪的证据判定 |

这些变化属于实验工件准备与运行条件的实现。W／H／R、owner、非抢占、生命周期资格及已有调度动作继续决定真实 worker 是否允许停止和重建会话。

## 3. 保留范围和身份

### 3.1 必需镜像集合

准备阶段冻结整轮可能调用的运行路径，取所有允许路径所需镜像的并集。采用同一 `retention_scope_id`、同一 Docker daemon 身份和完整镜像 ID 管理。实验启动按 ID，构建所需的名称映射另行核对。Docker 本机镜像 ID 和镜像仓库 manifest digest 分字段保存，不能互相替代。

| 对象 | 本轮持有要求 | 解释 |
| --- | --- | --- |
| 最终 worker 镜像 | 必须 | 镜像包含实际运行需要的层，模型资源仍使用已冻结挂载 |
| 本地受管模型服务镜像 | 可能在本轮启停时必须 | worker 和服务都要能在释放后按原 ID 重启，共享服务按镜像 ID 去重 |
| 原生对照或评分器的运行镜像 | 本轮仍需启动时必须 | 原生臂执行完才轮到平台臂、或工作负载结束后才评分的情况都要覆盖 |
| 依赖环境和基础镜像 | 默认仅用于准备／构建 | 已有最终运行镜像可以独立启动，不要求中间镜像继续单独存在 |
| 检查解释器镜像 | 准备阶段使用，按需备份 | 若它实际参与本轮评分或执行，则按真实用途纳入必需集合 |
| 平台镜像 | 平台容器已经引用 | 实验中保持平台运行，已有更新检查继续生效 |
| 云端模型服务 | 无本机镜像持有 | 按原连接契约执行 |

只保留最终 worker 对单独运行这个 worker 足够。一次完整实验还要覆盖上述服务、原生和评价依赖。未冻结的新镜像不能在运行中临时加入。

所有必需镜像需要同时容纳在本机磁盘。模型只需按调度决定轮流进入 GPU。准备时检查磁盘可用量和配置的余量，镜像共享层按去重范围估算，并记录估算边界。还须为真实 worker 可写层、日志、输出和导入临时空间留出余量，不能把剩余空间全部用于保镜像。引用建立后这些层不再是可依赖的可回收空间。无法容纳本轮镜像及运行余量时，在准备阶段报告缺口并调整存储安排。

冻结清单同时记录实际启动配置及外部输入。挂载源码、权重、配置和输入数据沿用现有内容摘要及版本记录，读入目录尽可能只读，输出放在独立可写目录。仅冻结路径或将挂载设为只读，均不能阻止宿主侧修改原文件。大文件摘要在准备阶段核对，正式运行中不反复全量读权重来校验。启动时核对绑定版本、路径和轻量变更信号，结束后按既有证据规则复核，无法确认不变时明确标记条件未知。轻量检查不声称能检测所有外部修改。[Docker bind mounts](https://docs.docker.com/engine/storage/bind-mounts/)

### 3.2 引用容器的最小配置

由平台现有部署后端执行 `docker create --pull=never`，指定完整镜像 ID，只创建不启动。记录必须核对以下字段。

- 独立名称和标签，例如 `seampact-image-ref-<scope>-<image>` 以及 `io.seampact.role=image-reference`、所属部署、实验范围、冻结镜像身份。名称短串用于查找，完整身份用于核对和删除。
- `State.Status=created`、`State.Running=false`、`State.Pid=0`、实际 `.Image` 等于冻结 ID。显式设置重启策略为 `no`，关闭健康检查，网络为 `none`，无端口发布、设备申请或 GPU 挂载。
- 使用经过核对的普通非 GPU 容器运行时，显式覆盖入口为不会调用来源程序的占位入口。镜像自身的 ENTRYPOINT、CMD 和环境变量不会在创建时运行。引用创建接口不接收来源凭据或 worker 启动参数。
- 不挂权重、业务数据、Docker socket 或来源目录。引用容器不带真实 worker 的 group／instance 身份，不进行平台注册，也没有模型就绪状态。
- 先检查镜像声明的 `Config.Volumes`。Linux Docker 支持时，对这些目标配置独立的只读、小容量 tmpfs 覆盖，创建后核对没有持久卷或宿主目录挂载。目标不兼容或仍产生匿名卷时，本轮准备失败并清理本次对象，不能声称引用仅有微小磁盘开销。该处理须在真实 Docker 验证后启用。

最后一项处理镜像自带 VOLUME 的副作用。Docker 在 create 阶段就初始化卷，简单省略 `-v` 不能保证没有额外复制。[Docker create 卷初始化](https://docs.docker.com/reference/cli/docker/container/create/#initialize-volumes) · [Docker tmpfs](https://docs.docker.com/engine/storage/tmpfs/)

### 3.3 独立归属与并发

每个实验范围、每个 daemon、每张唯一镜像建立一个引用容器。同一轮多个运行组、副本和策略臂复用它。两个实验使用同一镜像时，各自创建引用容器，镜像层仍由 Docker 共享。某轮结束只删本轮引用，避免维护一套容易在异常退出后失真的共享引用计数。

平台持久保存实验范围、冻结镜像清单和每个引用的容器 ID。创建使用确定性名称和唯一操作身份。创建超时后按记录位置重新查询，确认归属与镜像一致才接续。重复点击准备或收尾操作具有相同结果。名称相同但归属不同、镜像不同或状态已运行时，报告冲突。

同时保存创建时的 Docker 连接定位和 daemon ID，引用观察与清理均先核对这个位置。当前后端配置已切换时，不能拿旧容器 ID 去新 daemon 删除或把新位置“查无此容器”当成旧位置已经清理。原位置不可访问则记待核对，沿用现有未决对象处理。

引用记录独立于 `runtime_instance`，不进入 `_held()`、运行组容量、owner 租约、缩容候选或模型成本统计。正在运行的实验范围通过自身锁约束更新及工件修改。已经结束的范围留下一个待清理引用，只显示待清理事项，不能据此伪造一个未释放 worker。

整轮对冻结工件的修改限制与子运行对真实实例的使用锁分开。现有 `run_locks` 仍使用子运行 ID，整轮保留记录检查这个子运行是否属于允许的范围。子运行 `unlock()` 不能解除整轮的工件保护，整轮记录也不能使自己的子运行被误判为“其他运行占用”。实现采用已有锁与持久记录做短时状态检查，Docker 命令和长时间等待放在锁外，不增加长期持锁或通用任务队列。

## 4. 整轮执行流程

### 4.1 进入准备

1. 生成实验范围，确定来源、工件、运行依赖和候选镜像清单，获取本轮相关工件的准备锁。准备操作与平台内的定向镜像删除互斥。范围状态为 PREPARING，正式冻结清单尚未发布。
2. 逐张检查实际本机镜像。存在且身份一致就复用。明确缺失时，可按操作者已选备份导入并核对 ID，或从已配置仓库取得精确工件。只有需要生成新工件且无可用副本时才构建。恢复后同时检查当前平台与 worker 协议、核心工件及绑定是否兼容，旧镜像 ID 恢复成功不代表能通过当前平台注册。平台升级后若需新 worker，优先复用兼容的依赖环境构建新最终镜像，在准备阶段确定新清单。
3. 每张镜像一旦准备好，立即创建并验证引用，避免等所有大镜像构建完后才保护第一张。构建依赖或检查解释器需要临时持有时，复用同一引用创建机制，用 PREPARATION 归属覆盖其使用期，操作完成即释放临时引用。
4. 全部引用核对成功后，再整体复核镜像 ID、daemon 身份、数据／权重位置、来源运行条件及磁盘余量。检查成功才发布不可变清单并转为 READY_TO_RUN。部分失败时记录准备失败，清理本次已创建的引用，保留可复用镜像及原错误。已有副本也可在操作者选定后于此阶段备份，避免本轮结束解除引用后才想导出、却已被节点回收。
5. 完成本轮配置要求的冷／暖初态布置，随后进入正式调度窗口。镜像导入、构建和备份有独立的准备时间线。原有暖态预热的实际成本继续记录在原约定的运行测量阶段。

模型权重、分词器和原流程必需的本地资源也在准备阶段按现有绑定核对，所需下载提前完成。真实模型加载时的本地读取计入原加载成本。外部云端推理调用仍按原任务语义计量。

镜像检查和 create 之间存在外部回收竞争。create 成功并核对引用后才算持有成功。若此时镜像被删，准备仍未完成，重新准备的成本留在准备阶段。

### 4.2 调度与再次启动

每次运行开始以及后续冷启动、增加副本或启动依赖服务前，部署层统一核对实验范围、daemon、引用状态和冻结镜像 ID。自动按需启动、调度器动作、手动原生驱动与页面启动使用同一规则。

真实 Docker worker 和服务都用冻结 ID 创建，并设置 `--pull=never`。检查成功但创建仍失败时，按实际错误分类。只有明确的镜像缺失才能记 IMAGE_MISSING，连接失败、权限错误和不可观察分别保留原因。

检查放在分配新运行实例和写入加载开始事件之前。create 竞争失败时，准确记录是否创建了容器，只对真实创建的对象执行原释放流程，防止留下伪运行槽。各动作的错误类型向上传到实验运行器，避免被通用“启动失败”处理再次计入模型加载历史。

开始检查前登记本范围的在途启动操作。检查、提交、取得结果及超时后的对象核对完成之前，该操作不能从收尾条件中消失。关闭范围先禁止新的启动操作，再等已有操作和真实实例确认结束，最后才删除引用。只看到“当前没有 READY worker”不足以宣布本轮结束。超时不等于 Docker 没有创建容器，须按本次确定性身份查实。

调度器释放真实 worker 时按原路径排空、stop、rm，并等待后端确认。其引用容器保持 created。下一次创建新 worker，使用同一冻结镜像，生成新的实例代次和会话。

运行中发现镜像缺失、身份不符、daemon 改变或引用丢失，终止本轮后续派发，记录 PREPARATION_FAILED 及发生阶段 RUNTIME。已有请求按原非抢占和 owner 规则排空，已执行结果和资源记录持久保存。即便有备份，也转到新一轮准备后才导入。引用丢失而镜像暂时还在，同样视为本轮保留条件失效，避免继续等待真正丢失。

每次真实冷启动前实查所需的引用和镜像，整轮准备与结束时核对完整集合。后台巡检可复用已有周期，但不新增高频全库扫描，不在每次策略候选枚举或每个暖态请求时执行 Docker 命令。引用检查本身的耗时单列，并在所有对照采用相同策略，整体墙钟与平台 CPU 观测保留该开销。检查超时／连接失败记为不可确认，不能直接改写为 IMAGE_MISSING。

一次真实启动成功后，再核对新容器的实际镜像 ID，启动的进程必须对应原冻结镜像。引用从 created 变成 running／exited 也视为异常，按精确归属核对处理，不能因为 GPU 未使用就把这个状态当作有效持有。

### 4.3 正常结束、失败与平台重启

整轮收尾按以下次序执行。

1. 停止接收新的实验子运行和请求，等待已登记的执行任务、在途启动操作及 owner 收尾。预先登记的结果采集与评价尾部仍持有本范围使用资格。
2. 完成依赖本轮运行镜像的结果采集与评分，保存已有结果、资源记录及失败情况。在线与评价阶段继续分别计量。已持久化并安排在独立后续范围的离线评分，可以独立准备其镜像。
3. 关闭剩余启动入口，收尾本轮拥有的真实 worker 及受管服务，按原规则确认释放。已不再需要的 worker 可在前面步骤提前正常释放。复用他人持有的服务时遵守其原租约。确认没有在途启动或未决对象后才能解除镜像保护。
4. 结束运行测量，保存本轮执行状态。再按精确容器 ID、所属实验和镜像核对，删除本轮 created 引用。保留镜像本身，允许节点随后回收。大镜像导出不放在这段收尾中阻塞或污染计量，按第 6 节在准备阶段或独立操作中执行。
5. 将引用清理结果单列。删除失败记 CLEANUP_PENDING，可以重试精确删除，不能把它记成运行实例驻留或推翻已取得的模型结果。

用户取消和准备条件失败也走收尾。若真实请求或 worker 释放状态未确认，保持 CLOSING 并保留相应引用，等待现有未决处理流程。不能在 `finally` 中无条件解除全部引用。

平台意外退出后，从持久记录和专用标签核对遗留引用。旧实验标为 INTERRUPTED，旧 worker 依现有规则核对和释放。已确认没有运行消费者后清理该实验的引用。状态未知时显示待核对，保留引用。不开按年龄自动删除活跃引用的计时器，也不让旧范围自动恢复成同一轮有效实验。

原生／平台手动分段配对使用一个显式的“准备本轮／结束本轮”范围，子任务完成不会自动收回引用。自动运行器负责自己创建范围的收尾，子运行只能结束自己拥有的范围。原生脚本执行前核对范围清单和真实 Docker 身份，并写出执行回执。

## 5. 准备失败、冷启动与暖态复用

| 情况 | 调度记录 | 成本处理 |
| --- | --- | --- |
| 开轮前导入、拉取、构建、创建引用失败 | PREPARATION_FAILED，阶段 BEFORE_RUN，保留实际原因 | 准备成本单列，尚未开始正式窗口 |
| 同轮镜像或引用丢失，无法继续冻结条件 | PREPARATION_FAILED，阶段 RUNTIME，整轮中断 | 镜像处理耗时不填写为模型加载时间，已有调用、排空和资源消耗照实保留 |
| 镜像已在本机，原 worker 已删除，创建新进程并加载模型 | COLD_START | 分列容器创建、进程就绪、模型初始化和预热。可测总就绪时延不能一概称为纯权重加载时延 |
| 原 worker 或受管服务仍运行，所需模型已经按契约就绪 | WARM_REUSE | 记录派发、排队和执行，不虚构一次新加载 |
| worker 进程存在，但所需模型尚未初始化 | MODEL_NOT_READY | 按实际初始化事件计成本，不能归入暖态 |
| 原生 CLI 每请求启动模型子进程并退出 | 原生 PER_REQUEST_LOAD | 即使承载它的 worker 常驻，模型加载仍按每次原调用记录 |
| 镜像有效后真正的 OOM、模型初始化异常或服务超时 | 原运行失败类别 | 维持已有调度失败与成本语义 |

磁盘镜像已在本地，CPU 页缓存、下载缓存与 GPU 模型驻留是不同状态。冷启动定义不自动要求清空操作系统页缓存，各对照使用同一预先声明的缓存和初态安排。

原生臂、规则基线和 RL 臂均采用相同镜像准备与引用规则。PREPARATION_FAILED 的范围不能作为一轮完整执行报告，并记录失败位置及原因。结果是否进入主比较按事先声明的比较单元判断。失效前完整完成且冻结条件有效的单元保留，受中断影响的不完整单元不进入完整配对的主比较，同时报告失败数量及已经发生的工作和成本。已经执行或已到达的任务留在原记录中，不能删除失败样本后重新计算收益。单个臂已结束而配对臂未结束，仍属于不完整单元。

模型初始化缺乏单独时间戳时保留加载时间 UNKNOWN，使用真实可测的进程／调用就绪时延并说明范围。检查耗时从模型加载分项中分开，端到端请求时延仍涵盖请求实际经历的等待与检查。

在 joint 窗口失败汇总处阻止镜像缺失生成模型加载负奖励及加载成本样本，当前失效窗口设为不可用于更新。当前 `run_windows()` 在窗口返回后立即按 `eligible` 更新学习器，因此失效标记必须在窗口返回前形成，不能等外层捕获异常后才补。实际模型 OOM 等原有失败仍保持原算法语义。此前完整窗口已产生的学习历史保留，但异常结束的该训练运行不能自动激活为有效训练成果。重跑该运行从原声明的起始 checkpoint 和种子开始，用新范围身份保存。

镜像持有与备份不新增 RL 动作。模型准备、驻留、释放的真实耗时和成本仍属于原调度问题，镜像工件准备具有独立计量阶段。

## 6. 操作者选择的备份与定向清理

### 6.1 前端呈现

在现有镜像／运行环境页面增加镜像清单，按实际镜像 ID 去重后列出各用途。每项包含用途、来源／运行组关系、完整 ID、标签、本机状态及检查时间、正在持有它的实验、镜像大小与共享层提示、备份文件状态及恢复核验状态。

本机状态使用 PRESENT、MISSING、UNKNOWN。备份状态分别显示未备份、导出中、导出及摘要校验完成、文件缺失／损坏、成功恢复核验时间。历史 BUILT 作为构建记录展示。文件存在只能证明可读和摘要一致时的归档状态，成功恢复需由实际 load 后的 ID 检查证实。

操作者勾选 worker、依赖、基础或检查解释器镜像，选择已有可写归档目录后导出。操作卡展示预计空间、目标文件系统及可用余量、恢复／清理会影响的具体工件。运行中的实验保护集合不可删除。

### 6.2 保存与恢复

- 使用 `docker image save/load` 保存镜像。使用完整 ID 导出，保存来源工件、依赖 recipe、原基础 ID、平台架构及 SHA-256 摘要，避免依赖可变标签。容器 export/import 不用于保存冻结镜像。
- 一个选择可导出为一个包含多张镜像的归档，归档内共享层复用。按包含的镜像 ID 展示覆盖范围。删除备份以归档文件为单位，确认页面列出受影响的全部镜像，不能让用户误以为只删除其中一张。
- 直接写入操作者选择的有空间目录，使用同目录临时文件，成功、完成摘要与基本内容核验后才原子发布。空间不足或导出失败时，半成品不会被登记为可恢复备份。精确清理本操作的半成品。
- 平台容器必须实际看得到归档目录。前端显示平台内路径和已确认的宿主路径映射，检查目录所在文件系统及可用空间。没有合适挂载时给出部署配置缺口，在实验前由操作者配置。个人目录如果仍位于拥挤的系统盘，也不作为本次大镜像备份目的地。
- 导出目标的空间和 Docker 导入目标的空间分别检查。归档放在独立磁盘，load 仍会写入 daemon 的镜像存储，需要足够的新增层及临时空间。压缩归档大小不能直接充当导入空间。平台容器自身的根目录空闲量也不能冒充宿主 Docker 存储空闲量。沿用宿主准备检查取得正确文件系统回执，无法确认时明确报告缺口，不新增特权挂载或自动迁移 Docker 目录。
- 导出期间由临时引用持有选中镜像，完成后释放。恢复期间取得准备／导入锁，先查本机，存在同一 ID 则跳过。load 成功后核对全部预期 ID、架构和工件信息，再创建本轮引用。
- 恢复预先声明的同一镜像归档可以恢复原镜像身份。普通重建若实际 ID 发生变化，就生成新的实验清单，不能替换旧清单中的 ID。load 不能恢复 Docker 之外的权重、业务数据、宿主驱动或运行时凭据，这些按现有绑定分别核对。
- 保存最终 worker 的完整层足够恢复该 worker，但不能据此声称单独的依赖镜像对象和构建器缓存也已恢复。希望下次修改 worker 代码仍复用依赖时，应一并选中依赖环境及所需基础镜像，并按原 recipe／base ID 规则复用。pip 缓存和 BuildKit 缓存继续使用现有机制，镜像归档不承担它们的导出。

恢复后还须让已有构建器能定位依赖。当前 `backends.build()` 先按 `requested_base` 查基础镜像，再按 `dependency_image_reference(recipe, base_id)` 查依赖镜像。仅恢复一个无标签 ID 可能导致后续重新 pull 或重建。备份元数据保留已核对的构建名称映射，恢复后核对 ID、recipe 与 base ID，再补回缺失的本平台依赖名称。名称已指向其他 ID 时报告冲突，不能覆盖共享标签。基础镜像可使用核对过的内容专用本地名称作为本次准备输入，仍按原 base ID 验证。旧备份不能把用户新选的基础版本悄悄改回去。[Docker image tag](https://docs.docker.com/reference/cli/docker/image/tag/)

默认建议按使用目的勾选。继续跑同版实验优先保最终运行镜像，经常更新平台或来源代码时再保昂贵的依赖环境及其确切基础输入。依赖 recipe 改变时按现有规则决定能否复用，备份不提供跨不兼容依赖版本的复用承诺。同 ID 的现有有效归档继续复用，多个选择共享一个归档以减少重复层，无需自行实现分层归档系统。

镜像归档和导入能力沿用 Docker 官方接口，归档摘要校验与实际恢复核验分列。[Docker save](https://docs.docker.com/reference/cli/docker/image/save/) · [Docker load](https://docs.docker.com/reference/cli/docker/image/load/)

### 6.3 清理和测量互斥

前端分别提供“删除选定归档”和“删除选定本机镜像”。归档删除核对精确路径、归档身份和正在进行的导入／导出。删除镜像核对精确 ID、当前容器引用、本轮持有、构建任务和其他使用者声明，使用无 force 的定向删除，并带 `--no-prune` 防止连带删除未选择的无标签父镜像。一个 ID 对应多个名称时，显示全部关联名称。遇到多标签或他人归属冲突就保留并提示，不以自动 force 绕过。共享基础镜像默认只展示，由操作者明确确认归属和不用状态后才可删除。[Docker image rm](https://docs.docker.com/reference/cli/docker/image/rm/)

每次确认后的实际执行前再核对，避免页面打开期间发生新引用。正式计量阶段，平台在同一 daemon 上的构建、下载、导入、备份及清理操作被执行时检查拒绝，提示计量结束后重试，减少磁盘和 CPU 竞争。正在进行的大镜像操作也必须结束后才能进入计量。READY_TO_RUN 的等待阶段可完成已选备份，但相关冻结工件和引用仍不可修改或删除。已有外部共享负载仍按原实验观测协议记录。同一平台在相同测量资源上不同时运行两组本应独立比较的正式窗口。多个范围独立持有同一镜像只解决清理归属，并不自动获得实验资源隔离。

整轮结束自动操作只删除本轮引用容器。镜像和备份的长期清理由操作者选择，后续实验可先复用仍在的本机镜像。备份按 ID 和已有已校验覆盖跳过重复导出。

## 7. 引用容器的保护边界

| 外部操作 | 影响 | 平台行为 |
| --- | --- | --- |
| 只清理无容器引用镜像 | 有效引用可以保住镜像对象 | 每次启动前核对 ID |
| BuildKit 构建缓存 GC | 可回收构建缓存，不等价于删除已加载并引用的最终镜像 | 本轮继续用最终镜像，下一轮构建收益按实际缓存确认 |
| `docker container prune` | created／已停止引用容器可能被删除 | 引用缺失即中止本轮 |
| `docker system prune`，尤其带 `-a` | 可能先删引用容器，再回收镜像 | 同上，准备阶段明确节点的清理边界 |
| 定向删除引用容器、强制删镜像、重置 Docker 存储或迁移到另一 daemon | 可破坏保留条件 | 明确失败并保存结果，使用新范围恢复 |
| kubelet 通过 cri-dockerd 共用 Docker | 取决于具体版本的运行时删除行为及节点容器清理范围 | 核对 created 引用在本机的保护效果，不能把标签视为 Kubernetes 认可的免清理标记 |

标签用于平台识别与定向清理。外部清理只有主动使用排除规则时才会尊重这些标签。若节点会删除所有未运行容器，应由管理员在实验期间排除本平台引用，或换到具备适合保留规则的 Docker 环境。备份可降低下一轮恢复成本，无法保证遭到外部删除后的同轮调度仍有效。[Docker container prune](https://docs.docker.com/reference/cli/docker/container/prune/) · [Docker system prune](https://docs.docker.com/reference/cli/docker/system/prune/)

只做同一轮、镜像已经可用且节点保留 created 容器时，引用容器就够了。跨天、多轮重复、跨机器或需要节省下一次重新构建成本时，增加选定备份。对共享节点不自动停用 kubelet、不改全局 GC 阈值。

## 8. 实施顺序和代码落点

| 顺序 | 工作项 | 复用现有入口 | 完成条件 |
| --- | --- | --- | --- |
| 1 | 实验范围、冻结镜像闭包和引用记录 | 现有 store、实验 manifest、`training.py` 的外层 `_run()` 及原生配对入口 | 整轮边界明确，子窗口结束不解除引用，手动分段有显式结束操作 |
| 2 | 引用容器创建、核验、幂等清理 | `hosting/backends.py` 的 Docker 命令与身份核验，部署管理层 | 同 daemon 按冻结 ID 持有，重复操作和部分创建失败可正确收尾，处理 VOLUME 副作用 |
| 3 | 冷启动前核验和运行失败归因 | `deployment.py`、`managed_services.py`、`joint.py`、原生驱动 | 所有实际启动路径均禁止中途 pull/build/load，失效统一停止本轮 |
| 4 | 范围收尾、异常遗留与更新检查 | `training.py` 外层收尾、现有实例释放、`operation_preflight.py` | 引用不进入 worker 占用统计，运行中范围阻止不相容变更，安全收尾后引用可删 |
| 5 | 可选备份目录、镜像清单与精确操作 | 现有运行环境／部署页面、已有后台操作模式和镜像身份记录 | 可选导出与恢复，空间与挂载明确，半成品不算备份，清理边界可审查 |
| 6 | 指标和文档同步 | 原观察阶段、实例事件、失败汇总及镜像复用说明 | 准备失败／冷启动／暖态复用独立，旧实验记录保留原口径 |

新增的镜像持有逻辑集中在现有 hosting 层，由实验运行器调用。具体采用小模块还是现有类内方法，在实施时按复用程度选择，不增加独立服务或部署系统。功能入口同时覆盖自动运行与操作者发起的原生配对，不能只给一个脚本加特殊处理。

首要完成条件是同一冻结镜像在真实 worker 多次删除后仍能启动，其次是失效时保留结果并正确归因。引用记录不改变调度动作集合，备份界面不成为这一核心闭环的前置条件。状态沿用已有运行记录，增加范围身份、阶段和必要失败原因即可，不为每个准备步骤新增一套状态机。

## 9. 实施后的必要核验

以下保留完整设计核验清单。已完成的开发机软件核验及未覆盖条件，按[本地核验记录](../部署与操作/实验镜像保留与备份.md#本地核验记录)分别报告，不将其推广为真实来源实验或目标研究节点验收。

1. 用真实 Docker 从冻结镜像建立 created 引用，启动真实 worker 后排空删除，再用同一 ID 创建新代次。核对引用始终无进程／GPU申请，真实 worker 的释放状态和 GPU 归还正确。这是核心功能验收。
2. 连续多个调度窗口、策略臂和原生／平台分段间引用持续存在，最后统一结束后精确删除。检查评分尾部仍需的镜像也被覆盖。
3. 两轮引用同一镜像，一轮收尾后另一轮仍持有。重复准备、重复收尾及创建成功但响应中断时均无误删。并发提交启动与结束范围时，结束操作等待在途提交核对完成，子运行释放锁不解除父范围保护。
4. 对带 VOLUME 的实际小镜像检查引用创建的磁盘和挂载副作用，确认 tmpfs 覆盖行为。支持条件不满足时准备阶段给出明确失败。
5. 在隔离 Docker 测试环境中主动移除测试引用／镜像，验证后续启动产生准备条件失败，没有隐式拉取、导入或重建。共享实验服务器不做全局 prune 验证。
6. 导出选中镜像到指定目录，核对摘要，导入后验证同一 ID。覆盖备份盘与 Docker 存储空间分别不足、损坏归档、未知状态、名称恢复与冲突及一次多镜像归档的删除提示。恢复依赖后，以依赖未改变的源码更新验证实际跳过依赖安装。定向删除不连带删除未选父镜像。
7. 检查引用未进入运行槽、存活实例、驻留积分、显存统计和 warm 判据。真实模型冷启动、暖态复用及 CLI 每请求加载分别验证。
8. 检查中断窗口在返回学习器之前标为不可更新，不自动激活异常训练运行的策略。已执行任务、未决释放和实测费用保留。一个完整配对结束后下一个配对失败，前一单元仍可独立查证，失败单元不会被拼接成完整结果。
9. 准备阶段发现平台协议或绑定不兼容时不进入计量。正式运行不做全库 Docker 扫描或反复权重哈希。核对新增检查的调用频率及独立耗时字段。

小镜像与替身用于实现核验，真实来源运行用于研究结果。镜像导入和引用准备完成后再开始各策略的正式调度计量。

## 10. 本轮实现范围外

- 不让真实 worker 为保镜像持续运行，不保留真实 worker 容器却伪造 `released=true`。
- 不在运行中导入、下载、构建或替换镜像继续同轮比较，不把镜像准备失败计作模型加载成本。
- 不在排空或收尾时全局 prune，不自动清理共享基础镜像、卷、权重或其他使用者容器。
- 不把大归档写进已拥挤的系统盘，不通过修改系统存储、kubelet 或 GC 配置取得保留条件。
- 不实现跨节点镜像调度、容器热迁移、旧 worker 会话接管、长期备份服务或新的 RL 奖励。
- 本轮设计首先适用于同一 Linux Docker daemon。Kubernetes 多节点部署须有节点级镜像准备和身份核验方案，当前引用不能跨 daemon 提供保证。

## 11. 交付与后续决策

推荐先实施整轮引用、启动核验和准备失败归因，使真实 worker 的停启可以稳定参与调度实验。随后补操作者选择的镜像备份和定向清理，减少跨轮下载与重建。所有变更依上述方案完成核验后再进入真实配对。

部署前确认归档目录实际挂载与空间，并在目标节点验证其清理策略是否保留 created 引用。两者分别决定是否启用可选备份、当前节点是否满足正式实验的镜像保留条件。当前代码状态以[操作与限制](../部署与操作/实验镜像保留与备份.md)、[当前实现](当前实现.md)和[镜像构建说明](../部署与操作/镜像构建与依赖复用.md)为准。
