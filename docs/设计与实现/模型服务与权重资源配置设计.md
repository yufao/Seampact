# 服务、权重与资源归属

资源配置服务于 [平台自动接入设计](Harness接入与调度重设计讨论.md)。下面描述目标分工；当前登记与手动操作见 [资源配置操作](../部署与操作/资源配置操作.md)，实现范围见 [当前实现](当前实现.md)。

## 只收集确实缺少的信息

平台从源码、依赖清单、默认配置和说明中识别服务、模型权重、加载参数及环境要求。已登记且唯一匹配的资源自动绑定；构建、运行组归属、依赖传递和按需启动由生成的部署计划处理。

需要用户提供的是缺失凭据、无权自动取得的权重或确实冲突的选择。先读取已有配置再询问，不要求用户为每个入口重复填写模型、资源数组和参数映射。估算资源需求可用于准备，实际容量决策仍需有效观测或保守上界；无法确定时提示具体缺口。

## 三种资源关系

| 资源 | 平台职责 |
|---|---|
| 外部已经运行的兼容服务 | 保存命名连接及凭据引用，调用并记录可取得的请求用量；不管理外部进程生命周期 |
| 平台受管模型服务 | 管理实例初始化、共享使用、占用与释放；所有使用者经同一实例身份计量 |
| 能力内部加载的权重 | 登记文件与版本，按能力的实际加载方式使用；生命周期归属该能力实例 |

外部服务和受管服务可以使用同类 HTTP 接口，但接口相同不等于平台都有关闭权限。容器存活也不证明模型已加载或模型仍常驻。

对话、分析和教师是配置角色，不是必须部署的三个独立模型。普通聊天只用对话角色，源码分析按需用分析角色；有程序评分器时不必调用教师。多个角色可以引用同一资源，但各自请求语义和用量仍可辨认。

## 版本、共享与更新

生成计划记录源码、配置、权重和依赖的实际版本。更新登记不会悄悄改变已经执行中的任务或冻结实验。新绑定核对后用于新的调用；失败时保留现有可用版本并说明原因。

模型共享要求实际实例、权重、配置和隔离语义相容。同名连接、模型名称或两个容器使用同一路径，都不足以证明内存可以共享。独立部署也不要求强行共享模型。

共享实例的 RAM／VRAM 时间积分计一次；请求级分摊如有需要，另说明规则。预留容量、进程或容器实际占用、整张 GPU 的观测分开记录。远端无法观测的内存不填零，本机其他程序的整卡占用不归到某个 Harness 名下。

## 凭据与跨环境

密钥保存在现有凭据存储或环境变量中，能力描述只引用它。运行环境需要实际可达的服务地址和有效挂载；开发机的路径不能直接作为其他机器的可用资源。

平台和来源依赖分别管理。按仓库声明生成可执行环境，使用已有镜像和包缓存；Python、CUDA 或系统依赖冲突须解决后才运行，不能用静态文件存在代替真实初始化成功。具体安装与部署用现有操作文档，不再维护一份重复的版本建设计划。
