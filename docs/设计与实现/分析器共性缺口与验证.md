## 2. 按程序结构归纳，而不是按库名放行

| 共性问题 | 实际样例及核验结论 | 应补的通用能力 | 验证时必须保留的拒绝条件 |
| --- | --- | --- | --- |
| 证据归属与范围 | RefChecker 把参数定义写在 `mapping.evidence`，原检查器只读取依赖总 `evidence`。已有证据被当成缺失；另有证据只引用多行调用的一行 | 每条映射使用并校验自己的证据；诊断区分缺字段、缺参数定义、调用范围不完整、数据流未支持 | 空或越界证据不能回退到别处放行；其他入口的证据不能证明本入口 |
| 跨函数／构造器传参 | VPC3 的外层参数进入 `OpenAICompatibleBackend`；REX-RAG 的 `perform_single_search_batch` 把 URL 交给 `call_search_api`。后者直接 HTTP 映射通过，外层转交不通过 | 解析确定的调用目标，建立实参—形参映射，按有限调用链连接到实际资源使用点 | 同名函数但导入不同、动态目标、重赋值、未调用嵌套函数、未知分支不得仅凭名字接受 |
| 构造保存属性，稍后使用 | RefChecker 构造器保存 `self.model/self.api_base`，请求方法再交给批处理函数；VPC3 后端保存模型名后放进请求字典 | 追踪同一实例、属性写入时点及后续读取；支持范围须写清楚，未知变更保留未决 | 另一个实例、请求间改写、条件初始化、同名字段覆盖不能混为同一资源 |
| SDK 语义字段与代码参数名不同 | RefChecker 直接批处理的 `model` 单独检查通过，`api_base` 对应平台 `base_url` 却不通过；扩大证据范围仍无效 | 使用按 SDK 与调用签名组织的字段描述，解析真实导入及版本；原代码字段保持不变 | 不把任意函数的 `api_base`、`model` 都认定为资源；动态替换或同名自定义函数须拒绝或补证 |
| 资源定位方式被混为本地路径 | MiniCheck 的 Hub 标识经分支变量 `ckpt` 或 `self.model_id` 进入加载器。现检查不支持该分支来源和 vLLM 调用；两个需求扩大到整文件证据仍未通过 | 区分本地文件／目录、Hub 模型及修订号／缓存、附加 checkpoint、模型包／索引；追踪加载器真正消费的值 | Hub ID 不能直接解析成仓库下同名字目录；`config.json` 存在不能证明权重分片齐全；不能把任意分支都当成已选分支 |
| 初始化不止构造函数 | PIGuard 原 `eval.py` 先构造模型，再执行 `load_state_dict(torch.load(...))` 和设备迁移，随后评价；候选 `classify` 未承接 checkpoint 加载 | 调查原调用者的构造与初始化序列；能用已有构造绑定则保留原序列，超出现有规则时保留更大原入口并明确缺口 | 不允许略过 checkpoint 后用随机分类头“跑通”；不能把 `torch.load` 返回对象伪装成现有文件参数；不能自行改变对象寿命 |
| 配置对象／CLI 控制多资源 | MADL 的 YAML → `MADLConfig` → `resolve_weight` → factory/runtime；REX-RAG 的 CLI → `Config` → 检索器 → 常驻服务 | 先恢复原配置与消费关系，再检查资源位置；区分请求参数、启动参数和生成的对象。配置类、CLI、配置框架分别有有限支持条件 | YAML 路径不能冒充字典参数；解析 CLI 不能忽略环境变量与覆盖优先级；未核验的配置不得自动补默认值 |
| 入口角色与生命周期混杂 | 六来源候选中出现训练、合成数据、索引构建、服务启动、评价和在线推理；预处理已有在线／离线标签，但未约束最终目标目录 | 对入口的任务角色作结构化记录，默认能力目录只呈现目标及必需组件；准备／服务启动归入原生命周期 | 不能按文件名排除整个 `eval.py`，也不能把服务启动当成一次请求；隐藏根入口不应删除它被目标调用所需的代码 |
| 条件依赖与操作提示不一致 | VPC3 的服务需求被候选标为 `required:false`，但服务入口实际放入了该需求引用；准备说明跳过可选需求，服务路径缺口可能被另一项资源缺失遮住 | 区分依赖在原仓库可选、在当前所选入口／分支实际启用、在本次调用必需；提示与执行解析使用同一关系 | 可选且未使用的分支不能阻塞另一入口；显式使用的引用不能因 `required:false` 从缺口清单消失 |

三类错误必须分开处理：

1. **候选不完整／证据不对**：例如 RefChecker 的三个固定资源描述缺少 `placement`。当前却报“源码中没有固定路径表达式”，应先明确缺的是候选字段。修候选生成与反馈，不应扩大源码规则来掩盖。
2. **规则支持不足**：例如跨构造器、配置对象、属性传递。扩大引用到整文件不能解决，继续让用户补文件也不能解决。
3. **外部条件待提供**：映射已核对后，才进入选择真实服务、模型版本、文件及 worker 环境检查。平台进程未装某包与目标 worker 缺包也须分别报告。

## 3. Harness 的界定与分类建议

研究中的 Harness 宜界定为：**围绕一个明确目标调用，组织模型／服务、输入处理、检查或修复、控制流程和结果返回的可定位程序及其必需运行闭包。** 一个仓库可同时包含多个这样的目标、训练脚本、评价代码和展示界面，仓库本身不是单个 Harness 的充分定义。

面向本研究再增加任务角色：防护决策、补证／检索、宿主流程、独立评价。检索器不因进入能力池就自动成为防护决策器；普通聊天模型和前端也不会因可调用而成为防护成果。保持既有 10–15 个独立来源与真实工作集范围，按角色报告覆盖，不能拿辅助函数数量填充防护来源数。

建议以**入口／调用闭包**为分类粒度，多轴标注，可同时具备多个特征，不给整库强行贴唯一标签：

| 轴 | 要回答的问题 | 对分析流程的作用 |
| --- | --- | --- |
| 任务角色 | 目标防护、补证组件、宿主、初始化／清理、训练／评价、展示／测试，还是未确定？ | 确定导出的目标范围，保留排除依据；MOCK 需要数据来源与实际调用证据，不能只看名称 |
| 工作阶段 | 输入检查、检索补证、模型推理、输出核查、反馈修订、裁决？ | 追踪输入、结果消费者和原分支，防止把前后阶段随意互换；不预设所有来源都有这些阶段 |
| 程序形态 | 函数、对象方法、工厂／配置驱动、CLI／服务、工具／工作流、异步／循环？ | 决定读什么源码、采用哪种参数和构造检查；异步和循环不应直接排除整个来源 |
| 资源与生命周期 | 资源在哪里加载，模型／索引由谁持有，哪些状态跨请求保留？ | 确定准备、请求和关闭范围；不能由“在线方法”推断可并行、可远程或可长期保留 |

当前 `classification.py` 已有 `forms/families/traits/recipes`，预处理也已有 `execution_role`。问题不是从零再造分类器，而是分类输出仍主要引导阅读，缺少从“角色和结构”到“待核验条件、证据链、适用检查器及未覆盖原因”的明确连接。

可先约束自动承诺，而不是要求原作者重写代码遵守新标准：

- 固定来源、目标工作量、原配置与资源版本，能定位原入口和结果含义。
- 自动识别在声明支持的程序形式内进行；动态注册、反射、复杂配置和外部调用不能确定时，明确保存未知边，优先考察原入口整体接入。
- 整体接入仍需原环境、资源和调用条件成立。细拆、并行、对象保留等继续经过已有 W／H／R 与生命周期检查，分类不发放许可。
- 必须人工修源码或指定专用包装才能接入的，记为辅助接入并保存工作量，不计入无辅助自动成果。

以上是支持范围建议，不修改现有拆分理论。它允许复杂 Harness 以原入口进入研究，同时诚实地区分“支持整体运行”和“能自动细拆”。

## 4. 借鉴什么，以及不能借鉴出什么结论

| 一手来源 | 可以借鉴的机制 | 在本项目中的边界 |
| --- | --- | --- |
| [PyCG，ICSE 2021](https://arxiv.org/abs/2103.00587)，已核对论文正文 | 通过跨过程赋值关系解析 Python 调用目标，连接变量、函数、类和模块 | 借用实参—形参、赋值与调用目标图的组织方法；调用图不证明资源兼容、语义等价或可并行 |
| [IRIS，2025 修订论文](https://arxiv.org/html/2405.17238v3)，已核对第 3 节 | 静态分析先提取候选 API，LLM 推断语义规格，分析引擎按规格追踪，再结合上下文判断 | 可采用“LLM 提用途／资源候选，确定性检查器核对路径”的分工；原工作研究 Java 漏洞，不是现成 Python Harness 转换器，LLM 规格仍可能错 |
| [NeMo Guardrails，EMNLP 2023 Demo](https://aclanthology.org/2023.emnlp-demo.40/)及[官方阶段说明](https://docs.nvidia.com/nemo/guardrails/latest/about-nemo-guardrails-library/overview) | 把防护放在输入、检索、对话、执行和输出等具体位置，并区分配置、流程与动作 | 用于任务阶段分类；其声明式接口不能当成任意旧仓库已经满足的前提 |
| [DSPy](https://arxiv.org/abs/2310.03714)，已核对摘要与机制概述 | 用明确模块和接口表达 LM 管道，再交给编译／优化机制处理 | 借鉴内部统一表示；DSPy 优化的是按其模型编写的程序，不能据此声称无约束仓库自动转同构 |
| [LLMCompiler，ICML 2024](https://proceedings.mlr.press/v235/kim24y.html)，已核对论文页 | 区分调用规划、任务派发与执行，显式表示函数调用依赖 | 可对照规划与执行的职责；工具调用可并行不等于任意有状态对象方法可并行，也不直接证明 RL 优于启发式 |

资源语义也应有明确依据：[Transformers 文档](https://huggingface.co/docs/transformers/main_classes/model)区分 Hub 模型 ID、本地模型目录和缓存目录；[LiteLLM 文档](https://docs.litellm.ai/docs/completion/input)说明 `base_url/api_base` 的别名关系。实现 SDK 描述时仍须核对来源实际使用的版本，不能用最新文档替代冻结依赖验证。

据此建议的流程是：源码索引与目标角色 → LLM 提有证据的入口／资源候选 → 参数、配置与对象来源关系 → 按适用条件机械核对 → 原环境初始化和目标调用 → 满足现有规则后有限拆分。统一的是平台内部对调用、资源、状态和结果的描述，不要求所有原库源码长成同一种形式。

分类与 RL 的关系是：分类和核验给出合法动作、依赖、资源持有者等事实；真实运行给出负载、时延和占用。只有不同请求与资源复用之间确有跨时段权衡，才有进一步验证 RL 收益的依据。分类数量与库的异构程度本身不能推出 RL 更优。

## 5. 本次已做的局部修复与验证

在通用 `dependencies.py` 中修复逐映射证据被忽略的问题：有 `mapping.evidence` 时使用并验证它；未提供时才使用依赖总证据。空值、格式错误、越界范围和不匹配原参数／完整调用的证据仍不放行。

本次新增 4 项必要测试，覆盖跨文件证据、无效证据不能回退、不完整多行调用、不同入口不能互借证据。依赖检查相关 13 项测试和接入反馈相关 9 项测试通过。

用相同真实候选复放后，25 条资源检查维持原结果，RefChecker 的一条需求错误从“缺参数定义”推进为“尚未证明实际字段使用”；它仍为 MISSING。没有将任何来源虚增为可运行，也没有修改来源算法、权重或远端候选。

另外做了定位用对照：扩大实际源码证据范围；逐个核对 RefChecker 的模型／地址字段；为 REX-RAG 外层的真实 URL 参数构造仅用于诊断的映射。证实了第 2 节的字段别名、跨过程和分支来源缺口。这些人工改动只用于诊断，不是自动分析成果，也不是正式效果／资源实验。

## 6. 后续改动顺序与逐项验证约定

优先顺序按影响目标接入的共性组织：

1. **候选与反馈准确性**：补齐候选字段诊断、条件依赖提示、目标／辅助入口结构化角色。已有角色提示与用户勾选保留，不能把未核验角色写成事实。
2. **参数来源和 SDK 使用点**：从可确定的函数／构造器转交开始，逐步处理同一实例的受限属性来源。VPC3、REX-RAG、RefChecker 回查同一规则，不加入库名分支。
3. **资源定位与初始化闭包**：区分 Hub／本地／checkpoint／模型包；保留原构造后的加载、配置优先级和设备操作。MiniCheck、PIGuard、MADL 回查相应结构；先保留原入口，不能以删除初始化换取 READY。
4. **真实目标核验**：有原资源后，在既有平台跑原方法与接入方法的同输入／同配置调用，检查初始化、输出、失败行为及原效果，再进入完整调度实验。

每一项修复记录：程序结构、实际受影响调用、完整源码证据、候选是否完整、当前检查结果、允许范围、反例、真实库回查结果。规则级正反例负责检验实现，真实库负责检验实际覆盖；两者都不能替代原防护工作集上的最终效果与资源数据。

跨库验证要跨结构变化，而不是复制同一个片段改库名。例如跨过程规则须覆盖直接传参、经过别名、构造器转交；负例覆盖目标被覆盖、参数被重写、动态分派及作用域不同。选定某个配置分支的规则还须验证换一个分支会更新资源集合，不能把两套模型都强制要求或混用。

首批六库足够开始以上修复。该批次曾建议用 PaperGraph 核对图／工具／工作流入口；现已完成新增分析和第 8 节复查，因此不再把它称为未接触的留出来源。如后续需要补声明式防护配置结构，可再调查 NeMo Guardrails；目前优先修复已有样例暴露的共性，不为数量重复分析同类库。正式 10–15 库实验范围保持原协议。

## 7. 本轮核心支持实现与回查（2026-10-31）

以下是本地代码事实。原算法、W／H／R、并行及生命周期许可未扩大；本轮没有再次调用付费分析模型、下载模型、运行真实防护或修改服务器。

| 环节 | 已实现 | 明确保留的支持边界 |
| --- | --- | --- |

### 10.2 确认并修复的反馈缺陷

PaperGraphBench 五项服务需求把环境映射的 `read_time` 填成 `constructor` 或 `call`。这些入口确实是 CLI，平台需要在启动子进程时注入环境；原程序稍后在构造器消费变量，不会改变平台注入边界。旧代码把这类普通字段错误归入 `parameter_flow_unsupported`，反馈为 `model_repairable:false`，模型因此把可修候选当成规则缺口提交。

本地已按共性修正：

1. CLI 环境注入时点错误报告 `candidate_incomplete`，准确定位 `dependencies[i].read_time`，说明 `process_start` 与原消费位置的区别。函数宿主的临时环境注入仍保持规则不支持。
2. 资源引用在声明位置缺失或 id／field 不一致，报告候选可修项；不再笼统归入参数流规则不足。修改位置／引用后仍要完整核对真实消费链。
3. 没有 shebang 的 Python 脚本未声明解释器时，在解析资源之前返回 `cli_interpreter_missing` 和 `command.0`。显式解释器及原 shebang 形式继续按已有检查执行。
4. 分析提示明确上层宿主的间接资源责任，以及保留原设备／并发配置；提示增强与机械覆盖分别报告。

这些改动不支持任意 YACS、子进程环境传递或新拆分操作，也不替用户选择 CPU／GPU、并发数或服务。代码沿用 0.14.8，本次修正尚未提交、推送或部署。
