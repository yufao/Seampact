# 0.15.1 服务依赖与生命周期

2026-11-01 本地版本。本文说明受管模型服务的配置入口、执行边界和验证状态；研究机制、强基线及待运行实验见[联合调度规格第 9 节](部署前建设与调度动作方案.md#9-本地模型服务的依赖与生命周期调度2026-11-01)。原防护工作量、来源身份与真实效果仍须分别核对。

## 配置

在“配置 → 服务连接”中，可将连接标为云端、借用或平台管理服务。借用和云端连接不获得实例启停权。平台管理服务先在同一区域展开“登记受管服务规格”，填写 JSON 后保存，再于连接中选择其 id；连接的端点及模型须与服务规格一致。保存规格会核对本机已存在的 Docker 镜像并冻结内容身份，**不会下载镜像或启动模型**。相同 id 更新规格会重新核对；服务仍被使用或未确认释放时不能修改。

规格首版为单模型 OpenAI 兼容 HTTP 服务。主要字段如下：

- `id`：小写字母、数字和短横线，最多 40 字符；`model`、`model_identity`、`weight_identity` 分别记录实际模型名、可核对模型和权重身份。
- `image` 是本地已有镜像；`argv` 是镜像内服务程序的参数列表。不得在参数或规格中填写凭据值。
- `endpoint` 是无凭据的稳定 HTTP 地址；`docker` 给出容器端口，并在固定本机映射端口或专用网络及稳定别名中选一种，不能同时设置两种模式；可声明只读挂载、GPU 和 `pass_env` 环境变量名。挂载的 `source` 必须是后端主机绝对路径。GPU 用 `device=GPU-...[,GPU-...]` 明确设备，须与 `resource_envelope.devices` 的键完全一致；CPU 服务不填 `gpus` 且设备映射为空。挂载路径和凭据保存在本机配置，不放入共享材料。
- `contract` 明确 `control_owner`、`exclusive_control: true`、`request_isolation: true`、`rebuildable: true`、`background_work: false` 与正整数 `max_concurrency`。这些是部署者可核对的真实条件，不由平台猜测。
- `resource_envelope` 包含有依据的正数 `host_memory_mb`、`devices`（设备到 `memory_mb` 上界的映射，CPU 服务可为空）和 `basis`；`depends_on` 可声明已有服务 id 的依赖。实际包络须覆盖加载与允许并发，未知不可当作零。
- 可选 `health_path`、`models_path`、`key_env`、`start_timeout_s`、`probe_timeout_s`。环境变量字段只填变量名；健康及模型探针须符合实际服务接口。

以下是字段形状示例，不是可直接运行的服务；先用实际镜像、模型、启动参数和经测量的包络替换示例值，确认实例控制条件成立。

```json
{
  "id": "example-model",
  "protocol": "openai-single-model/1",
  "model": "MODEL_ID",
  "model_identity": "MODEL_VERSION_OR_DIGEST",
  "weight_identity": "WEIGHT_VERSION_OR_DIGEST",
  "image": "LOCAL_IMAGE_REFERENCE",
  "argv": ["ENGINE_COMMAND_AND_ARGUMENTS"],
  "endpoint": "http://127.0.0.1:18000/v1",
  "docker": {"container_port": 8000, "publish_host": "127.0.0.1", "publish_port": 18000, "mounts": [], "pass_env": []},
  "contract": {"control_owner": "EXPERIMENT_OWNER", "exclusive_control": true, "request_isolation": true, "rebuildable": true, "background_work": false, "max_concurrency": 1},
  "resource_envelope": {"host_memory_mb": 1024, "devices": {}, "basis": "REPLACE_WITH_MEASUREMENT_BASIS"},
  "depends_on": []
}
```

上面的端口和内存仅示意字段形状，不是默认容量或实际资源声明；`argv` 的每个元素应对应真实的独立命令参数。远程 worker 容器若要访问服务，需使用双方可达的固定网络别名与端口，不能把宿主机 loopback 地址误认为容器内地址。

服务连接卡片展示资源归属和已登记实例的运行／模型状态；未运行不代表模型已就绪。规格保存、连接验证、实际启动、模型就绪及原任务调用是不同事件。服务配置属于运行资源，不改变来源自身模型及接口；已有每次调用加载的 CLI 不因此变为常驻模型。

受管服务参与实验时须选择 `joint/1` 并填写完整容量和 `joint-costs/2` 资源权重；`functional/1` 会拒绝。普通对话模型和分析模型角色当前使用云端或借用连接；普通聊天中的 Harness smoke 可管理其自身服务依赖并持任务租约。连接检查与明确能力调用不会自动启动服务，须满足就绪、租约及实验锁条件。

## 联合实验配置与更新

受管服务实验使用 `scheduling_mode: "joint/1"`。`joint.capacity.resources` 的标准键为 `host_memory_mb` 和每张实际设备的 `gpu:<device-id>:memory_mb`；每个 worker／服务分配单元都要为这些键提供完整的 `demands`。服务的声明需求须覆盖其规格包络，包络本身须覆盖加载峰值和允许并发下的请求内存。共享服务使用同一个 `service:<id>`，不能为两个来源重复登记两份同一实例。若单任务完整依赖也放不下，配置会拒绝。

`joint.costs` 使用以下显式形式，各项权重在开发集确定后冻结；下面只说明字段，不能作为实际资源或收益结论：

```json
{
  "schema": "joint-costs/2",
  "task_seconds": 1,
  "instance_seconds": 0,
  "resource_seconds": {"host_memory_mb": 0.001}
}
```

GPU 实验还须在 `resource_seconds` 中填写全部已声明设备资源的权重。`resource_policy` 可选 `learned/1`、`fixed/1`、`queue_threshold/1`、`shared_lru/1` 或 `dependency_cost/1`。后两项配合显式 `retention: {"mode":"idle_retire/1","idle_ms":...}`；它们在共同合法候选中选择动作，分别按共享实例最近使用时间，或已观测加载成本、依赖等待和释放资源排序。加载统计没有样本时保留缺失标记；规则借鉴已有工作，但未称为原论文系统复现。

服务规格通过 `/api/managed-services` 登记，观察数据在 `/api/state` 的 `resources.managed_services`；实例准备及释放复用 `/api/deployments/start`、`/api/deployments/status`、`/api/deployments/drain-stop`，`group_id` 为 `service:<id>`。正式实验由调度器调用这些操作，实验持有实例期间手动操作会被拒绝。检查连接和明确能力调用不会隐式启动服务。

更新服务器后先核对平台版本。已有来源不必全部重新做模型分析：为受管依赖选择新连接后，沿正常绑定／零模型重新核对流程生成当前资源绑定。原分析若确实漏掉依赖关系，再从分析修订台补查并记录实际辅助来源。需要运行的 worker 在释放旧实例后重新导出和构建，以核对当前平台核心身份；权重不用重新下载。新增联合特征及成本版本要求创建新实验，旧策略不能静默加载为新版本策略。

首轮真实验证优先检查一个服务的冷启动、模型就绪、原库真实调用及停止释放，再检查两个来源共享服务，最后进行模型池超过容量的混合任务对照。每一步都保留原输入、必需工作量和独立质量评价；实际模型性能与 RL 收益由这些实验提供。

## 验证状态

整库回归 379 项中 377 项通过、2 项因本机缺少可选依赖跳过，无失败。最后新增服务网络目标唯一性检查后，19 项受管服务和 8 项联合服务调度检查再次通过。检查包括冷／暖态共享、实际教师评价路径、并发、超时未决保留、配置冻结、后端删除确认及采样未知；Docker 使用替身，本地 HTTP 探针实际运行。前端语法及已有 3 项摘要测试通过，临时本地页面人工核对了归属切换和规格编辑区。

本轮未下载模型、未启动远端服务，未提交、推送或部署。普通服务连接的保存继续不触发模型加载。

版本具体实现和本地检查结果以[当前实现](当前实现.md)为准。真实模型服务、跨来源共享、训练及完整工作负载对照需独立运行并留存证据，不能用配置保存或合成检查冒充。资源占用积分、质量与端到端收益亦待实际测量；保留原 TruFor GPU 调用记录及其每请求 CLI 边界。
