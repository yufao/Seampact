# 设计与实现路线

更新：2026-10-13，版本0.5.0。本文解释当前实现与后续理论接口；操作见[手动启动与演示](手动启动与演示.md)，汇报见[组会报告](组会报告.md)。

## 接入与拆分

引擎输入为来源固定修订、可见工件、入口描述、任务要求和允许的拆分操作。API Agent读取源码与数据／配置事实，根据通用准则提出边界；独立引擎核对锚点和生成产物。运行宿主保留原算法、原生状态与controller，包装接口；只在支持的局部结构上生成有限重构。

一个Harness可产出多个能力。能力边界与部署单位不同：共享状态的能力可以留在同一原生owner里，由门控暴露多入口。部署为进程／容器／Pod时以owner的状态和生命周期为单位，不能机械地把每个函数拆成独立容器。

W包装已有callable；H在框架注册前接线；R提取可验证的局部循环体。同一方法的整体门禁与内部R是互斥方案。源数据、Notebook非代码单元和配置随包保留，未知依赖明确记录。

当前分析后端是平台自己的工具Agent循环，成熟Agent应用可以作为后续替代后端。API负责提出方案，机械检查与固定SDK支持规则决定当前引擎能否构建；宿主再决定这个包能否兑现真实执行。人工为开发探针提供的边界不进入正式分析输入。

## 理论中的操作与判断

对同一边界分别判断原位排期、独立导出、并行和远程派发。输入／状态／owner／继续路径／效果／资源和SDK版本决定前提；未知影响哪种操作，就限制对应操作。原对象无法序列化可能限制远程化，但不必同时否定原owner内的排期。

原流程内接线`controller_bound`与导出供新组合`composition_export`分开。H接线只说明原流程经过门禁，独立导出还需初始化、输入与状态前提、作用域和唯一继续者。当前DEMO以原流程内排期为主，完整逐操作准入、独立导出目录和联合搜索尚未实现。

形式化目标分三类：T1限定环境／观察下的顺序轨迹精化，正常覆盖和进展另证；T2实际可达事件前缀上的合法交换；T3策略选择合法动作时的启动、身份、版本和托管资源不变量。定义与证明骨架已在研究工作区形成，具体规则的完整参数化可靠性证明仍待完成。

## 产物和运行

产物包含原工件、adapter、可选patched工件、固定来源请求、候选、转换记录和清单。API候选不能自签运行许可；引擎独立接收与宿主执行负责不同环节。

任务图含条件分支、资源与状态约束。调度先处理原控制流已经启用的动作，等待许可后才进入原body，结果交回原controller。当前DEMO实现单宿主FIFO，采用实际API与本地文本资料完成CRAG任务。原SDK无效果的StartEvent分支可以被终止清理取消，结果把逻辑调用与body进入分开显示。

能力包里出现多个边界，不意味着某次任务全部激活，也不意味着它们可以独立并行。并行要保持共同使能、相关状态、输出／外发／费用、异常与保护前缀，并满足整组资源条件；无数据依赖边不能代替这些条件。

## 当前实际实现

四源可以冻结与分析。此前真实DeepSeek工具分析中，CRAG和DiSP完整候选构建成草案，MMCT和ABC的完整提交被检查拒绝。当前业务宿主只支持固定CRAG修订及其有限接线方案；任务使用原Workflow方法和事件、本地输入资料与实际模型端点。

0.5.0真实CRAG任务复用已有API包，完成4次DeepSeek调用，返回中文答案，9项原生调用发生退休。平台新build包的package_id路径另经受控联调，保持精确选择，不替换成示例包。这两项不合并成一次新分析实验。

MMCT／ABC／DiSP完整任务、独立导出、并行、跨源组合、K8S业务执行后端与两层RL仍待实现。当前Docker默认是一个带CRAG SDK的工作台服务。

## 近期开发顺序

1. CRAG竖向切片已接通；继续改善实际任务与分析／包／运行交接，优先扩展MMCT图片任务。
2. 扩展MMCT图像、ABC政策配置、DiSP数据／CLI能力，优先实现可操作任务入口。
3. 增加能力族选择、条件任务图、状态／效果／驻留资源记录；在真实任务上接入合法并发和组合。
4. 调度先建立规则基线，再接两层RL：上层选择已验证的拆分／能力组合，下层决定执行顺序、并发和资源。K8S遵循同一owner及效果协议。

检查围绕新功能的实际问题进行，默认使用可操作DEMO推进；研究比较、消融和完整机制实验按论文问题独立开展。
