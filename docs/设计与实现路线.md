# 设计与实现路线

## 接入与拆分

引擎输入为来源固定修订、可见工件、入口描述、任务要求和允许的拆分操作。API Agent读取源码与数据／配置事实，根据通用准则提出边界；独立引擎核对锚点和生成产物。运行宿主保留原算法、原生状态与controller，包装接口；只在支持的局部结构上生成有限重构。

一个Harness可产出多个能力。能力边界与部署单位不同：共享状态的能力可以留在同一原生owner里，由门控暴露多入口。部署为进程／容器／Pod时以owner的状态和生命周期为单位，不能机械地把每个函数拆成独立容器。

W包装已有callable；H在框架注册前接线；R提取可验证的局部循环体。同一方法的整体门禁与内部R是互斥方案。源数据、Notebook非代码单元和配置随包保留，未知依赖明确记录。

## 产物和运行

产物包含原工件、adapter、可选patched工件、固定来源请求、候选、转换记录和清单。API候选不能自签运行许可；引擎独立接收与宿主执行负责不同环节。

任务图含条件分支、资源与状态约束。调度先处理原控制流已经启用的动作，等待许可后才进入原body，结果交回原controller。当前DEMO实现单宿主FIFO，采用实际API与本地文本资料完成CRAG任务。原SDK无效果的StartEvent分支可以被终止清理取消，结果把逻辑调用与body进入分开显示。

## 近期开发顺序

1. 跑通可交互CRAG任务，改善分析／包／运行的交接与进度，支持复用已有真实API产物。
2. 扩展MMCT图像、ABC政策配置、DiSP数据／CLI能力，优先实现可操作任务入口。
3. 增加能力族选择、条件任务图、状态／效果／驻留资源记录；在真实任务上接入合法并发和组合。
4. 调度先建立规则基线，再接两层RL：上层选择已验证的拆分／能力组合，下层决定执行顺序、并发和资源。K8S遵循同一owner及效果协议。

检查围绕新功能的实际问题进行，默认使用可操作DEMO推进；研究比较、消融和完整机制实验按论文问题独立开展。
