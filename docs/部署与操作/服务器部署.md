# 服务器部署：首次安装与更新

以下统一脚本适用于 Linux Docker 平台：首次部署使用 `bash deploy.sh install`，已有部署使用 `bash deploy.sh update`。镜像标签、构建参数和替换步骤由仓库脚本维护，实际源码与运行镜像分别核对。

命令在服务器的宿主终端执行。平台在容器内运行，默认工具镜像包含 Docker CLI 和 buildx，通过本机 Unix socket 使用服务器已有的 Docker daemon；不在平台容器中另起 daemon。容器内的 Python 仍为 3.11，Harness 的独立解释器和运行组按网页选择的环境构建。

GPU 选择需要协调平台能运行 `nvidia-smi`／NVML。仅有 Docker socket 或宿主机能运行 `nvidia-smi` 不代表平台容器可见 GPU。需要补观测配置时，可使用当前部署入口的 `configure` 操作：

```bash
bash ./deploy.sh configure --gpu-observe all --ready-timeout 600
```

`configure` 复用当前平台的精确镜像 ID，不拉取 Git、不构建镜像或安装依赖，沿用原数据挂载、端口、网络、空闲核对、停机备份和健康检查。入口脚本可以单独上传到私有工作区执行，无需先修改服务器源码克隆。不要混入 `--extras`、基础镜像或依赖更新选项；这些仍使用 `update`。仅配置运行容器不会改变所部署的 Python 源码身份。

`--gpu-observe` 接受 `all` 或逗号分隔的完整 GPU UUID，配置保存在私有部署记录并在后续更新中沿用。新增的设备请求只开放 NVIDIA `utility` 能力，用于 `nvidia-smi`／NVML，不分配 CUDA 计算能力；已有计算／其他加速器请求不会被这一选项覆盖。实际 worker 的 GPU UUID 仍在部署后端或运行组中单独指定。脚本先用本机现有镜像启动无状态挂载、无网络的临时观测容器核验 NVIDIA Container Toolkit；失败时不停止原平台。新平台启动后再核验一次 GPU 访问，失败时保留中断替换记录及备份，不自动回滚。NVIDIA 能力说明见[官方文档](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/docker-specialized.html#driver-capabilities)。本地模拟及一次真实 Linux 节点的同镜像配置、健康检查和容器内 GPU 查询均已通过；worker 模型推理及正式测量仍需分别核验。

本页是平台安装与更新的主入口。[Docker 网络与工具](Docker部署.md)解释网络和路径；[运行组远端操作](运行组远端操作.md)处理 worker；[运行组与 K8S](运行组与K8S部署.md)保留研究机制和 K8S 专题。版本功能与历史运行事实见[当前实现](../设计与实现/当前实现.md)，不再按版本复制部署步骤。

## 服务器实验的模型启停

Linux 上用同一用户的 systemd 管理实验和专用模型端点。办公比较服务与下方的一次性实验入口共用模型。最后一个实验退出后，回收程序等平台已接单的业务和能力调用收尾，再停止这次启动的模型服务和转发容器。启动前已经运行的服务由原使用者继续管理。回收只执行停止操作，权重、卷和实验记录继续保留。

在服务器源码目录安装用户入口，更新这些文件时再次执行即可。

```bash
install -Dm644 scripts/server_experiment.py ~/.local/lib/seampact/server_experiment.py
install -Dm644 deploy/seampact-experiment-models.service ~/.config/systemd/user/seampact-experiment-models.service
systemctl --user daemon-reload
```

在私有文件 `~/.config/seampact/experiment-models.env` 中配置本机已有的实验端点。多个名字用空格分隔。容器使用当前用户的 rootless Docker。下面为字段示例，按服务器实际服务名、容器名、Unix socket 和平台地址填写。使用外部业务 API 时，这里只登记仍在本机运行的检查服务及其转发容器。配置文件在下一次启用端点时生效。

```ini
SEAMPACT_MODEL_UNITS="office-chat.service office-guard.service"
SEAMPACT_MODEL_CONTAINERS="office-chat-bridge office-guard-bridge"
SEAMPACT_MODEL_SOCKETS="/path/to/chat.sock /path/to/guard.sock"
SEAMPACT_EXPERIMENT_PLATFORM_URL=http://127.0.0.1:8880
SEAMPACT_EXPERIMENT_PLATFORM_CONTAINER=office-platform
```

`seampact-office-development.service` 指向早期固定权重开发序列，不是当前五目标方案的通用启动入口。新运行使用下面的入口，把实验名和命令替换成当次已核对的冻结运行命令。整个训练和独立评分由前台命令管到结束。进程正常返回、报错退出或收到停止信号时，systemd 均会处理模型资源。实验日志可用 `journalctl --user -u <实验名>` 查看，模型回收日志在 `seampact-experiment-models.service`。

```bash
python3 ~/.local/lib/seampact/server_experiment.py run "$RUN_NAME" /usr/bin/python3 -u "$EXPERIMENT_DRIVER" "$@"
```

连续训练可给 `run_office_pilot.py --training-only` 传入 Unix 时间戳 `--admission-deadline`。到时在下一个完整派发段前停止接题，等待在途业务与评分，结算 PPO 并保存检查点。正常暂停的退出码为 75。下一次用 `budget-stop.json` 中的冻结协议、同一原生评分器和新输出目录运行 `--training-only --resume-training`。它从记录的下一题开始，恢复优化器与随机状态，奖励分母沿用完整训练集。暂停边界的服务冷启动计入新段。

服务器校准也可指定派发截止时间，并通过 `--stop-on-missing-api-usage` 在完整派发段检查最终用量。驱动或评分出错时，办公驱动请求收尾当前拥有的工作负载，等待业务与实例释放，保存停止结果。`--drain-timeout-s` 控制驱动等待收尾的时间，到期仍未释放的状态保留在停止回执中。服务器托管作业应保留独立输出目录，并另设最后的资源回收步骤。

Linux 本机模型可用 `measure_experiment_models.py --business-unit "$CHAT" --guard-unit "$GUARD" "$OUTPUT" -- COMMAND ...` 包裹训练命令。每个已结算段输出受管能力、共享检查模型、业务模型及合计的 RAM、VRAM 时间积分和覆盖时长。采样按这两个用户服务的 cgroup 和 GPU 进程归属计量。宿主、代理、工具和评分器另属基础设施。PPO 的资源奖励沿用受管能力的账目。训练服务可在 `ExecStopPost` 调用 `server_experiment.py release-workers "$OUTPUT" "$DATABASE" "$PLATFORM_URL"`，按本轮任务 ID 和容器身份释放完成或异常留下的实例。原始数据、模型权重和镜像保留。

## 更新当前工作树

确认待部署代码已提交并上传至所选远端，待分析、任务、训练和 worker 收尾后，在已有部署的源码目录执行：

```bash
bash ./deploy.sh update --with-tools
```

`--with-tools` 也接入 Docker 存储只读核验挂载。若此前使用轻量平台、现在要运行学习器，再加 `--extras rl`；已有 `rl` 构建选项会自动沿用。自定义部署根目录时仍加原来的 `--root`，尚无部署记录的旧平台按第 3 节接管，不把已有数据当首次空目录安装。

更新后从实际访问的平台地址打开 `/health`，核对 `status` 为 `ok`、`version` 为待部署代码版本。版本一致不能证明未提交修改已进入镜像，仍须核对实际部署源码和工件身份；单独刷新浏览器不会升级后端。

检查器或 worker 执行代码变化时，按当前规则核对已有候选并重新生成匹配的工件；无需仅因平台更新重复调用模型分析未变的来源。保留原仓库、持久权重、数据与可复用依赖镜像。实际需重新准备的范围以源码、依赖和工件身份为准，见 [镜像构建与依赖复用](镜像构建与依赖复用.md)。更新不会自动开始实验或续跑中断训练。

## 1. 执行前提

服务器已有 Bash、Python 3、Git、Docker CLI、buildx 和当前账号可访问的本机 Docker 服务。构建使用该 daemon 的默认 Docker builder。脚本不安装系统软件，不修改共享服务器的 Docker 权限或 context。选定 daemon 后，后续操作使用保存的同一 Unix socket，不会因新终端切换 context 而误操作另一套服务。

```bash
command -v bash python3 git docker
docker version
docker buildx version
docker context show
```

使用个人 rootless Docker、服务尚未运行时，按已有安装情况执行：

```bash
systemctl --user start docker
docker context use rootless
docker version
```

执行安装或更新期间不在网页提交新分析、任务或训练。更新前先等待现有工作收尾，在“运行组与部署”排空停止并释放旧实例；脚本发现运行／排队的工作或尚未释放的 worker 会停止更新，不替使用者中断研究运行。K8S 中的平台沿用 K8S 专题操作，本脚本管理本机 Docker 平台。

当前实例的 `STOPPED` 不代替实际后端释放。更新预检若报告控制器异常，先核对活动任务、未决调用及原容器的实际存在性；旧控制器自身异常无法恢复时，由操作者在确认工作结束和资源释放后停止该平台容器，再执行普通更新，保留原数据和错误证据，不修改状态库伪造 READY。

更新前可打开“运行与资源”查看阻塞原因；进行中的资源记录也需先停止。更新脚本复用预检后继续执行原有检查。指标范围见[性能探针与测量协议](../研究实验/性能探针与测量协议.md)。

## 2. 首次部署：服务器还没有代码仓库

从同一待部署版本取得仓库根目录的 **`deploy.sh` 单个文件**，用 SFTP 上传到服务器自己的家目录。脚本可独立执行，不要求先有 Git 克隆。仓库 URL 使用目标机器已有的 Git 授权，不在 URL 中附带 token 或密码。

```bash
read -r -p '仓库 URL（不含凭据）: ' SEAMPACT_REPO_URL
bash "$HOME/deploy.sh" install --repo "$SEAMPACT_REPO_URL"
```

默认工作区为 `~/seampact-workspace`：

| 路径 | 内容及保留方式 |
|---|---|
| `Seampact/` | Git 源码；更新只快进拉取，不自动丢弃本地修改 |
| `data/` → 容器 `/data` | 配置、凭据、分析与任务记录、状态库、冻结源码、策略及导出包 |
| `harnesses/` → 容器 `/harnesses` | 自己放置的来源、数据及权重；更新沿用原挂载 |
| `deployment.json` | 私有部署记录：容器、daemon、构建选项、镜像归属等 |
| `platform-environments/`、`platform-build.json` | 平台依赖精确锁、已核验镜像身份和本次构建记录；后续更新继续读取 |
| `platform-input.lock` | 显式导入锁的私有副本，仅使用 `--dependency-lock` 时生成 |
| `backups/` | 更新前停机复制的完整 `/data`，以及私有容器配置 |

已有 Git 克隆、还没启动过平台时，直接使用该克隆：

```bash
git -C /path/to/Seampact pull --ff-only
bash /path/to/Seampact/deploy.sh install --code-dir /path/to/Seampact
```

`install` 在目录不存在时克隆源码，但不会替已有克隆执行 `git pull`；使用上面的手动快进更新后再安装。`update` 默认先快进拉取，`--local` 才跳过拉取。构建开始时核对脚本打印的版本与实际待部署代码；相同版本号不代表源码身份相同。

自定义工作区、端口并安装三学习器所需依赖时：

```bash
bash "$HOME/deploy.sh" install --repo "$SEAMPACT_REPO_URL" \
  --root "$HOME/seampact-workspace" --port 8880 --extras rl
```

`--extras rl` 安装学习器依赖，默认空值为轻量平台。只有不需要网页准备解释器、构建或管理 Docker worker 时，才在首次安装加 `--without-tools`。其他首次配置包括 `--container`、`--data-dir`、`--harness-dir`、`--network`；完整参数执行 `bash deploy.sh --help`。配置被保存，日常更新不用重新填写；自定义 `--root` 后，每次仍使用该工作区。

首次安装拒绝已有同名容器或非空状态目录；原容器仍存在时按下一节接管，原容器已删除时明确使用下述 `--reuse-data`，避免无意创建空平台。

## 3. 更新：服务器已经部署过旧版本

### 已经由本脚本管理

```bash
bash "$HOME/seampact-workspace/Seampact/deploy.sh" update
```

自定义工作区时继续加 `--root /path/to/workspace`。脚本读取保存的容器和构建选项，在当前分支执行 `git pull --ff-only`，然后重新进入拉取后的脚本。更新命令无需填写版本号。代码须已提交并上传到所选 Git 远端；本机未推送的变化不会出现在服务器。

`--local` 用于已由自己更新好的干净 checkout，只跳过 `git pull`，仍执行构建、备份和容器替换。它不允许忽略本地修改，也不表示直接重启旧镜像。

### 办公实验实例的首次接管

先提交并推送包含 `src/seampact/pi_host/`、办公实验源码和部署文件的完整版本；在服务器私有工作目录内新建干净克隆和独立部署记录目录，不覆盖既有平台源码或数据。确保所选 Docker context/`DOCKER_HOST` 指向原实例的本地 rootless daemon。Git 使用服务器已有授权，不把凭据放进仓库 URL。

```bash
bash "$SEAMPACT_CODE_DIR/deploy.sh" update \
  --root "$SEAMPACT_DEPLOY_ROOT" --code-dir "$SEAMPACT_CODE_DIR" \
  --container "$SEAMPACT_PLATFORM_NAME" --extras office,rl --with-tools \
  --agentdojo-bundle "$SEAMPACT_AGENTDOJO_BUNDLE"
```

`office` 固定 AgentDojo 源码提交并保留可校验的 Git 工作树；`rl` 是需要学习器时的额外依赖。离线 bundle 为可选项，必须含固定提交；省略时从公开上游获取。脚本将 bundle 复制进私有部署记录供后续更新使用；依赖及基础镜像同样按构建记录保存。接管沿用现有数据、harnesses、端口、网络、PID 模式、设备请求和 Python 工具镜像设置；`--with-tools` 校验所选 daemon 的 socket 和只读存储挂载。不要传 `--gpu-observe all` 来替换原先单卡选择。新镜像在停旧容器前检查固定源码和工具镜像，并把旧办公镜像的专用运行锁路径切换为新镜像中实际生成的锁。

首次重新解析得到的 Python 包版本未必与旧办公镜像一致；若要求延续旧环境，先提供经核验的完整精确锁及相应来源，使用 `--dependency-lock`，并确认实际环境。否则保存新构建记录，在新锁上重新冻结整组实验，不混用旧结果。更新之前排空任务，保留旧镜像和停机备份；后续使用相同 `--root` 执行 `update`。普通 Compose 默认值不包含这一实例的全部特殊配置，不用于接管它。

### 旧版本通过 docker run 启动，尚无部署记录

取得新版本的单独 `deploy.sh`。填写原平台的**准确容器名**和已有代码目录：

```bash
read -r -p '原平台容器名: ' SEAMPACT_OLD_CONTAINER
bash "$HOME/deploy.sh" update \
  --container "$SEAMPACT_OLD_CONTAINER" \
  --code-dir "$HOME/seampact-workspace/Seampact"
```

脚本读取原配置，保留 bind／命名卷／匿名卷的实际身份、读写属性、环境变量、容器用户、补充组、端口、网络、启动命令和资源配置。原来使用 host 网络时继续保留，不自动改成 bridge。已有状态目录无需改名或搬到新默认目录。

旧平台没有 Docker 客户端和 socket、现在需要网页操作 Docker，或需要接入本次存储核验挂载时，在更新中加 `--with-tools`。它构建工具镜像并挂载当前选定 daemon 的 socket 和存储核验路径；若原挂载指向另一 daemon，会先报错，不替换原挂载。后续沿用同一构建配置。若服务器连代码克隆也已不存在，可提供 `--repo` 重新拉取；原数据仍以原容器挂载为准。

### 原容器和镜像已删除，旧数据目录还在

先确认当前及其他运行位置没有进程写入该状态目录。对本机选定 daemon，脚本会额外检查可写挂载是否重叠。明确指定旧数据目录，用 `install --reuse-data` 重建平台，例如旧指南默认的数据目录为 `seampact-data`：

```bash
bash ./deploy.sh install --reuse-data \
  --code-dir "$PWD" \
  --container "seampact-platform-$(id -u)" \
  --data-dir "$HOME/seampact-workspace/seampact-data" \
  --harness-dir "$HOME/seampact-workspace/harnesses" \
  --with-tools --extras rl
```

`--reuse-data` 仅用于 `install`，必须提供已有的 `--data-dir`，其中须存在 `platform.sqlite3`。脚本先构建镜像、创建保持停止的新容器，再从该容器的 `/data` 挂载复制完整停机备份，成功后才启动原目录。不会清空、迁移或用新目录覆盖旧数据；备份包括数据库、WAL、配置和目录内其他文件。`--extras rl` 对应需要学习器的部署，可按原用途选择。

原容器已删除后，Docker 不能再提供它的旧端口、环境变量、网络或额外挂载；此路径使用新平台的 bridge 网络和默认端口，需要的自定义配置须依据原记录补齐。目录外的权重、来源和环境变量凭据也不因数据库文件仍在而自动恢复。旧数据是否完整、实际任务是否可运行仍须以恢复后的结果为准。完成后使用普通 `update`，不重复执行恢复安装。

### 旧版本通过 Compose 启动

首次接管需要明确把平台后续管理交给本脚本：

```bash
bash "$HOME/deploy.sh" update \
  --container "$SEAMPACT_OLD_CONTAINER" \
  --code-dir "$HOME/seampact-workspace/Seampact" --adopt-compose
```

接管保留原容器配置和网络，仅移除平台容器的 Compose 管理标签。此后统一用 `deploy.sh update`；不要再对旧 Compose 项目执行 `up` 来重建该平台。原项目其他服务、网络与卷保留。若继续由 Compose 管理，则保留原私有环境文件和同一项目，按[Docker 说明](Docker部署.md)处理，不混用两个管理入口。

`--rm`、共享其他容器命名空间／卷、links 等不能直接接管的情况，会在停止原容器前报出原因。平台须使用标准启动入口和 `--home /data`，且 `/data` 有可写的持久挂载；只存在于容器可写层的数据，须先完整迁出并显式挂载，再接管。

## 4. 更新顺序与数据保留

1. 核对部署记录、原容器及挂载；检查 Git 工作区，再快进拉取。
2. 按实际版本、commit 和本次构建标识构建核心镜像；需要工具时再构建工具镜像。原平台此时仍在运行。
3. 核对工作已收尾，创建尚未启动的新容器，检查 Docker 是否接受原配置。
4. 停止原平台，将完整 `/data` 复制到新的私有备份目录，再让新容器使用原数据挂载启动。
5. 新容器 `/health` 返回预期版本，所需 Docker 工具可用后，才删除原平台容器，清理符合条件的旧平台镜像。

删除旧容器不带 `-v`。配置、历史结果、冻结来源、模型和权重继续位于原持久挂载中。原来临时在容器内安装的依赖或写到未挂载路径的内容不会自动进入新镜像；依赖应进入构建声明，持久文件应进入挂载目录。

备份复制的是**已停止平台的整个 `/data`**，包含 SQLite 及其 WAL／辅助文件、配置、策略和部署材料，不在运行中单拷 `.sqlite3`。外部 Harness、数据与权重保留原挂载，不默认重复备份大模型。备份文件由运行脚本的宿主账号拥有；恢复时按原容器 UID/GID 和挂载方式核对拥有者。[Docker cp](https://docs.docker.com/reference/cli/docker/container/cp/)

备份可能包含凭据，只保存在私有工作区，不进 Git，也不把 `deployment.json` 或 `container.json` 全量贴到聊天。原配置和数据挂载仍保留，因此不要把旧容器或 `docker commit` 镜像当成数据备份。

构建失败时原平台继续运行。替换途中或新版本启动失败时，脚本保留原容器、镜像、数据挂载和已完成的备份，停止继续更新；若新容器已经写入状态，先恢复停机备份再考虑运行旧版本，不直接拿旧镜像读取可能已变化的状态。脚本不自动执行数据回滚。

平台重启会更换 session，保留历史不等于恢复内存中的模型对象或在途调用。更新后从网页启动新 worker 实例；平台核心、协议或安装身份变化时重新生成运行包、构建 worker 镜像，见[运行组远端操作](运行组远端操作.md)。

## 5. 旧容器和镜像的清理范围

| 对象 | 脚本处理 |
|---|---|
| 本次被替换的原平台容器 | 新平台报告预期版本后删除；失败时保留 |
| 本脚本构建的核心／工具镜像 | 保留最近两次成功部署，仅删除更旧、归属本部署且无容器引用的标签 |
| 接管前已有的镜像 | 保留；仅凭名称或旧版本号不能判定归属 |
| worker、目标 Python、CUDA／模型基础镜像 | 保留，由运行组生命周期与实际用途决定 |
| 宿主数据、权重、Docker 卷、网络 | 保留 |
| 状态备份、Docker 构建缓存 | 保留，不纳入每次更新自动清理 |

重复执行定向镜像清理：

```bash
bash "$HOME/seampact-workspace/Seampact/deploy.sh" cleanup
```

不执行全局 prune，不强制删镜像，不按 `seampact-*` 名称批量删容器。未引用不表示没有研究价值，尤其 worker 重建可能涉及原依赖和 CUDA。接管前的旧镜像需手动核对准确 ID 和全部容器引用，再用不带 `-f` 的 `docker image rm`；删除一个标签不一定释放多标签镜像的层，见 [Docker image rm](https://docs.docker.com/reference/cli/docker/image/rm/)。

## 6. 手动命令与报错处理

显示概要；不打印完整环境变量或私有容器配置：

```bash
bash "$HOME/seampact-workspace/Seampact/deploy.sh" status
docker logs --tail 80 seampact-platform
```

捕获到的命令／Docker API 失败详情保存在工作区的私有 `last-error.txt`，终端只提示位置；构建进度直接显示在终端。本地查看该文件可得到原始错误，不将其中的凭据、路径或容器配置整体分享。

**rootless 启动时报 `setgroups: invalid argument`：** 2026-10-25 修正了工具 socket 附加组的设置：容器 root 已映射 daemon 用户时，不再追加宿主数字 GID；普通 Docker 保留按 socket GID 添加组。旧失败容器仍保留创建时的配置，单独更新源码或再次 `docker start` 不会重写它的 `GroupAdd`。先核对 `User`、`GroupAdd`、socket UID/GID 和 rootless 映射；若是从未启动的首次安装，须验证记录中的容器 ID、Created／未运行状态、`/data` 原挂载及完整停机备份后，移除该失败容器（不加 `-v`），保存原部署记录，再解除仅对应此次初次安装的 pending 并使用修复后的脚本恢复安装。已有旧平台的中断更新不适用该处理，仍按下文备份与回滚路径核对。此修正已完成本地构造核验，服务器启动结果待实际返回。

对上述已经核对的“首次安装、Created、从未启动、已有完整备份”情况，可在拉取修复后的干净源码后执行：

```bash
python3 deploy/recover_created.py --root "$HOME/seampact-workspace"
```

此工具使用现有部署锁，仅处理记录中的同一容器 ID；核对原数据挂载和备份后，先保存部署记录副本，再移除未启动容器并解除该次 pending。它不删除卷、镜像、数据或备份，不处理已有旧平台的中断替换，不启动新容器。任一身份或状态不符会停止。随后按第 3 节 `install --reuse-data` 使用同一数据目录重新安装。

已接管的部署使用原容器名。以下对应脚本内主要操作；手动替换前仍须保存原配置和挂载，不照新部署默认值覆盖旧部署。

| 环节 | 对应命令／动作 | 报错后处理 |
|---|---|---|
| 更新代码 | `git -C "$SEAMPACT_CODE_DIR" status --short`、`git -C "$SEAMPACT_CODE_DIR" pull --ff-only` | 先处理本地修改或分支分叉，不自动 reset／stash |
| 确认版本 | `git -C "$SEAMPACT_CODE_DIR" rev-parse HEAD` | 确认选定分支已包含需要部署的代码 |
| 构建镜像 | [统一构建入口](镜像构建与依赖复用.md#手动构建平台与工具镜像) | 核对基础镜像、依赖和实际错误，构建完成前不停止旧平台 |
| 停止原平台 | `docker stop "$SEAMPACT_PLATFORM_NAME"` | 先等任务收尾并在网页排空释放 worker |
| 备份状态 | `docker cp "$SEAMPACT_PLATFORM_NAME:/data/." "$SEAMPACT_BACKUP_DIR/data"` | 先创建备份父目录、保持原平台停止；核对空间和权限 |
| 查看新平台 | `/health` 及 `docker logs` | 版本或启动不符时保留原容器、镜像和备份 |
| 检查工具 | `docker exec "$SEAMPACT_PLATFORM_NAME" docker version`、`docker exec "$SEAMPACT_PLATFORM_NAME" docker buildx version` | 无 CLI 用 `--with-tools`；权限问题检查 socket、容器用户与补充组 |
| 删旧平台容器 | `docker rm "$SEAMPACT_OLD_CONTAINER"` | 确认是已替换且停止的那一个，不加 `-v` |

手动核心／工具镜像和 Compose 构建均按[镜像构建与依赖复用](镜像构建与依赖复用.md#手动构建平台与工具镜像)执行，不直接构建缺少 `DEPENDENCY_IMAGE` 的平台 Dockerfile。普通 `update` 沿用保存的依赖选项与锁；需要重新解析时显式加 `--refresh-dependencies`。包索引、PyTorch 版本／渠道、导入锁及清空已保存选项的方法也在同一说明维护。

容器创建、停机、改名、启动和移除对应 Docker Engine API 的 `containers/create`、`stop`、`rename`、`start`、`DELETE ...?v=0`。使用 API 是为了按原 JSON 保留配置，不需要将原凭据拼成 shell 参数。

处理中断的替换：先用 `status` 找保留容器和最新备份，查看本地容器日志。确认新旧平台均停止后，先将当前数据完整保存为另一份副本，再把停机备份恢复到**原挂载位置**，最后才启动对应原镜像／保留容器。bind 和命名卷的恢复目标不同，不套用同一删除／复制命令。处理后核对私有记录的 `pending`、当前容器和镜像字段；不要仅删 `pending` 来忽略未解决的状态或容器。

## 7. 打开网页与配置资源

默认平台发布服务器回环 `127.0.0.1:8880`。在自己的电脑建立 SSH 本地转发：

```bash
ssh -N -T -o ExitOnForwardFailure=yes \
  -o ServerAliveInterval=30 -o ServerAliveCountMax=3 \
  -L 127.0.0.1:18880:127.0.0.1:8880 "$SEAMPACT_SSH_TARGET"
```

`SEAMPACT_SSH_TARGET` 使用自己的 SSH 配置名或登录目标，不写进仓库。保持终端连接，在电脑打开 http://127.0.0.1:18880。服务器端口变化后同步修改转发目标。

Windows PowerShell 可在本机另开一个终端执行下面两行；使用非默认 SSH 端口时，给 `ssh` 加平时使用的 `-p` 参数。该命令保持连接而不启动远端 shell 命令。

```powershell
$seampactSshTarget = Read-Host 'SSH 配置名或登录目标'
ssh -N -T -o ExitOnForwardFailure=yes -o ServerAliveInterval=30 -o ServerAliveCountMax=3 -L 127.0.0.1:18880:127.0.0.1:8880 $seampactSshTarget
```

这里第一个 `127.0.0.1` 是运行 SSH 客户端的电脑；最后一个 `127.0.0.1:8880` 是 SSH 服务器所见的平台端口。当前聊天的本地工具与 SSH 客户端能访问同一回环接口时，可直接读取 `http://127.0.0.1:18880`。若工具实际位于另一容器或虚拟机，则先核对其访问宿主的地址、隧道监听地址及网络连通性；网关地址不能直接视为宿主回环的别名，不默认扩大监听范围。参见 [OpenSSH 转发说明](https://man.openbsd.org/ssh)与 [Docker 宿主连接说明](https://docs.docker.com/desktop/features/networking/networking-how-tos/)。

模型角色、命名服务、权重及依赖绑定见[资源配置操作](资源配置操作.md)。路径填写执行容器可见的 `/data`、`/harnesses` 或其他保留挂载；worker 的挂载 source 则由 daemon 按宿主路径解析，见 [Docker bind mounts](https://docs.docker.com/engine/storage/bind-mounts/)。Windows DPAPI 凭据不能直接作为 Linux 凭据迁移。

## 8. 手动执行与结果回传

操作者在服务器终端执行安装、更新、模型启动与实验命令。本地协作者通过隧道读取已有 HTTP 接口，查看实际状态、分析缺项及运行结果；启动和修改操作继续由操作者执行。隧道本身不提供任意 shell 日志或文件下载接口。

| 已有 GET 接口 | 返回内容 |
|---|---|
| `/health` | 平台在线状态与实际后端版本 |
| `/api/state` | 来源与生成状态、能力、运行组、任务和历史研究运行摘要 |
| `/api/analysis/ANALYSIS_ID` | 指定旧分析的只读记录与检查结果 |
| `/api/scheduler/runs/RUN_ID` | 指定旧研究运行的冻结 manifest、history、curves 和已持久化汇总 |

先读取 `/api/state` 中返回的完整 ID，再读取对应详情，不猜测 ID。分析记录和实验返回可能包含私有地址、路径及输入，下载到本地已忽略的 `.local-private/`，共享报告另做脱敏。接口读取不启动新的推理或训练；模型服务检查、调用和任何 POST 操作单独按操作者的执行安排处理。

旧 joint 窗口的物理观测摘要及文件索引在对应历史运行中；当前办公实验以其冻结协议和实际输出目录为准。需要原始文件、错误日志或策略文件时，由操作者用 SFTP／SCP 下载指定实验目录。保留运行身份、采集时间与文件摘要；正在写入的文件只算阶段快照，完整导出在工作结束后执行。运行目录可能含冻结模型配置和私有连接信息，仅存本地私有目录；不为回传结果公开整个 `/data` 或凭据目录，也不在运行中单独复制状态数据库作为备份。

当前工作树及研究节点可能处于不同提交；实际部署、镜像与工件身份须各自核对。平台更新、worker 准备、原模型运行、效果评价及正式调度实验继续分别记录，不由软件版本推定完成。
