# 实验镜像保留与备份

2026-11-03，本地实现，尚未部署至研究服务器。本机 Linux Docker 已完成两代真实 worker 的注册／调用／释放、同镜像重启、备份恢复、VOLUME tmpfs 覆盖和引用丢失中止核验。没有加载真实模型或测量 GPU 归还，不计作来源实验结果。设计边界见[改进计划](../设计与实现/实验镜像保留与备份改进计划.md)。

## 页面操作

进入“运行组与部署”，展开“实验镜像与备份”。

1. 先按原流程准备检查解释器、零模型重检、导出并构建／发布匹配当前代码的 worker。不要把旧 BUILT 当作镜像现在存在的证明。
2. 点击“刷新本机镜像”，查看完整 ID、用途、实际存在性、检查时间、引用范围和归档。刷新是显式操作，日常页面轮询不扫描 Docker。
3. 配置并核对 Docker 存储的位置。直接在同一 Linux 宿主进程执行时使用 daemon 的实际存储目录；平台运行在容器里时，须事先提供该文件系统的可核对挂载，再填写平台内路径。代码会根据平台容器的真实 bind mount 核对宿主来源，不能用平台可写根目录或远程客户端磁盘冒充 daemon 存储盘。无法核对时报告 `DOCKER_STORAGE_UNKNOWN`，不会开始正式计量。
4. 勾选本轮最终运行镜像，填写比较单元，例如 `[{"id":"pair-1","run_ids":["native","platform"]}]`。选择 worker 运行组时沿用 FrozenCatalog 补齐已绑定受管服务的依赖闭包；原生或评分器的额外镜像也须勾选。点击“准备本轮”，逐张创建独立引用，核对成功才显示 READY_TO_RUN。
5. 在 READY_TO_RUN 阶段可选择备份。确认正式任务流、初态、绑定及输入已经冻结后，点击“开始计量”。页面启动 worker 时，选择“用于页面启动”的本轮范围。真实 worker 仍按原流程排空、停止、删除；同轮再次启动使用原 ID，且禁用隐式拉取。
6. 完成所有子运行、调用和本轮评分，按正常操作释放真实 worker／受管服务，然后“结束本轮”。若尚有在途启动、TaskPlan、外部脚本票据、真实实例或服务租约，显示 CLOSING，引用继续保留。消费者结束后重试收尾。CLEANUP_PENDING 只表示独立引用待清理，不表示真实 worker 驻留。

自动研究运行由 `TrainingJobs.start()` 为同次提交的全部比较臂建立一个范围；窗口及单个臂收尾不会解除引用。最后一个子运行结束后尝试清理，未释放对象仍需核对。手动范围可在 READY_TO_RUN 阶段通过训练启动请求的 `retention_scope_id` 关联子运行；开始后不能临时扩充清单或新增未声明子运行。

引用容器始终不启动，使用普通 runc，无 GPU、网络连接、端口、业务挂载或凭据，不登记为运行实例。镜像声明的 `VOLUME` 目标使用只读、64 KiB 的 tmpfs 覆盖；本地真实核验没有产生持久卷或宿主挂载，创建后还会逐次检查。非预期卷副作用会使准备失败，并精确清理本次新建对象。K8S 节点与跨 daemon 的镜像保留不在该实现范围内。

## 手动原生、TaskPlan 与评分接线

所有接口沿用平台现有 HTTP 服务，结果写入现有私有状态库。

| 接口 | 用途 |
| --- | --- |
| `GET /api/images` | 显式读取实际镜像状态、范围和备份 |
| `POST /api/images/configure` | 核对并保存 `storage_path` 和 `reserve_bytes`（默认 1 GiB，可按工作量调整） |
| `POST /api/images/prepare` | `group_ids` 或冻结 `groups`、额外 `images`、`comparison_units`；返回范围 ID |
| `POST /api/images/begin` | 用 `retention_scope_id` 进入正式计量；检查镜像操作互斥 |
| `POST /api/images/verify` | 核对完整冻结闭包，适用于原生脚本执行前及最终条件复核 |
| `POST /api/images/usage` | 外部原生／评分脚本取得使用票据；结束后以 `action=release`、同一范围与 `ticket_id` 明确释放 |
| `POST /api/images/result` | 手动范围记录事先声明的 `run_id` 与 `status`，成功结果需再次核对条件 |
| `POST /api/images/close` | 关闭新启动入口，消费者结束后精确删除本轮引用 |
| `POST /api/images/reconcile` | 平台重启后，操作者确认旧启动操作已结束，再核对实际对象；只解除旧平台会话票据，外部脚本票据另行释放 |

外部脚本须持有 usage 票据，按返回的原完整 ID、同一 daemon 和 `--pull=never` 执行。脚本自行构建或导入新镜像不属于同轮执行。执行前核对实际容器镜像身份并保留回执；异常时先确认 Docker 对象及请求已结束再释放票据，不能在不明状态的 `finally` 中无条件宣称结束。

显式 `POST /api/plans` 可附 `retention_scope_id`。平台会登记任务票据，将范围传给实际启动入口，任务及原 owner 收尾、结果保存后才释放票据，整个范围由操作者结束。票据和范围字段会包含在请求身份中；冻结配对须明确任务负载与运行控制元数据的各自身份，不能与历史不同请求摘要冒称同一输入。

比较单元与保留范围分开记录。只有声明的成员均完整结束且条件有效，单元才记 COMPLETED。后续单元失效不回写此前已完成单元，未完成的单元不能拼接新范围结果。

## 可选归档

选择已有可写宿主挂载目录，勾选镜像后“备份选中镜像”。实际输出为同目录的 `<id>.tar` 和 `<id>.json`；同一归档可包含多张镜像并复用共享层。元数据保存完整 ID、平台架构、已核对依赖配方与构建名称映射、SHA256 和宿主目录映射。临时引用覆盖导出操作，失败半成品不登记为有效备份。已校验且覆盖相同 ID 的有效归档会复用。

最终 worker 归档足够恢复该 worker；希望后续更新代码时跳过依赖安装，应一并选择依赖环境及其确切基础镜像。归档同时核对传统 config 身份与 OCI 索引／manifest 的内容身份，保留 daemon 实际报告的 ID，不把它换成另一种摘要。镜像归档不包含 Docker 外的权重、输入数据、宿主驱动或运行时凭据。

恢复在新一轮准备之前执行。先复用本机同 ID，再从归档 load，核对全部预期 ID、架构和依赖标签；恢复缺失的本平台依赖名称及内容专用基础名称，已有名称指向另一 ID 时报告冲突，不覆盖。不会自动补写共享的可变基础标签；若原基础标签已经消失，在准备配置中明确选择恢复的 `seampact-build-input:sha256-<完整摘要>`，再按相同 base ID 与 recipe 复用，避免把新选基础版本悄悄改回旧版。平台升级后仍需按当前 worker 协议与核心代码核对；不兼容时正常生成新 worker，优先复用匹配依赖环境，然后建立新范围。

备份盘按镜像大小之和的保守上界及余量检查；导入另查 Docker 存储盘，按缺失镜像大小的两倍加余量预留新增层和临时空间。共享层、实际导入开销和运行输出按现场情况确认。设置更大的 `reserve_bytes` 可留出所需日志、输出及真实 worker 可写层空间。空间或挂载不可确认时不写入默认系统盘。

迁移时一起保留 tar 和 JSON。在“已有备份的元数据文件路径”填写 JSON，登记时重新核对归档摘要及所含镜像；文件路径按所选目录重新定位，不沿用旧机器绝对路径。归档完整校验和实际 load 恢复时间分别显示。

归档删除与本机镜像删除分开确认。删除归档须确认其覆盖的全部 ID；本机删除会再核对实验保护、容器引用、构建操作和标签，使用无 force 的 `image rm --no-prune`。多标签冲突保留，不执行全局 prune。正式计量期间拒绝平台内构建、下载准备、备份、恢复和清理。

## 失败和计量边界

启动检查在实例分配和 `start_wall` 之前执行，检查开销记录为 `check_ms`。实际冷启动、初始化、预热和调用继续使用原事件；缺少单独模型加载时间戳时 `model_load_ms` 为 UNKNOWN。CLI 每请求新进程不能因承载 worker 已绑定而标成模型暖态。

镜像／引用丢失、daemon 改变和绑定轻量信号变化会写 PREPARATION_FAILED（BEFORE_RUN 或 RUNTIME），禁止后续派发，同轮不自动 load、pull 或重建。正在进行的调用、资源记录和费用照实保留。joint 窗口在返回学习器前失效，奖励为 null，不调用 observe/update；异常训练运行不会成为可激活的成功策略。真实模型初始化异常、OOM 和原执行失败仍走原有类别。

挂载只记录既有绑定身份以及路径、大小、修改时间等轻量信号；目录内文件修改、宿主侧并发修改等不能全部由这些信号检出。正式输入／权重内容摘要和结束条件须继续按研究协议核对，不能从“镜像不变”推导数据不变。

引用保护仍取决于节点保留 created 容器；`container prune`、`system prune`、定向删除或 Docker 存储重置都可破坏它。标签仅用于归属核对。目标研究节点仍需复核清理策略及 GPU 模型释放，不能将开发机成功等同于该节点通过。

## 本地核验记录

普通 Python 检查和前端 16 项检查通过；真实 Docker 两项专项均通过：

- 用现有平台正常导出、构建并注册 worker，原轻量算术函数调用两次，两个不同实例代次均确认释放；引用覆盖停启间隔，镜像 ID 不变。
- 额外验证 VOLUME 镜像 created 引用的 tmpfs、无持久卷副作用；独立小镜像导出后精确删除，再由归档恢复原 ID。
- 主动只删除本次实验引用，后续检查记 RUNTIME／PREPARATION_FAILED，原镜像保留，无 pull、build 或 load 修复。

Docker 专项位于 `tests/test_image_retention_docker.py`，需显式设置 `SEAMPACT_DOCKER_TESTS=1`，只使用已有 Python／BusyBox 镜像，不拉取或全局清理。Docker Desktop 的存储位于 Linux VM；本次软件专项以独立只读 statvfs 探针提供准备空间回执，并替换测试的空间提供者，**没有宣称 Windows 客户端路径通过生产 `storage()` 的映射核对**。部署时仍按上文配置可核对的存储路径。所有测试容器、镜像及临时名称已精确清理，已有用户镜像保留。机器回显与构建回执只留本地私有目录。

实际核验发现并修复了两处模拟未覆盖的问题：当前 Docker 上下文不是 `default` 时应选择其对应的本地 docker 驱动构建器；Docker 模板读取缺省 Volumes 字段须使用安全的 map 访问。备份的 OCI 索引核验也由真实导出回执补齐。真实来源、多策略对照、依赖归档恢复后重建的实际节省及 GPU 归还仍未由本次软件核验覆盖。
