# Harness 分类、执行契约与调度的连接

更新：2026-10-31。本文响应新增三库复查，深化[主设计 18 第 3.1.2 节](../../想法/18_异构Harness拆分形式与RL调度设计.md#312-harness-特征分类与分析配方)。定位为**研究方案及实现建议**；既有 W／H／R、owner、生命周期与 joint/1 继续约束执行。下面的统一契约和条件性命题尚未作为完整算法实现或证明。实际代码及九来源证据分别见[当前实现](当前实现.md)和[核验记录第 8 节](分析器共性缺口与验证.md#8-更新后的九来源与新增三库核验2026-10-31)。

## 1. 研究对象与可承诺范围

实施补充：本地检查报告现提供 `execution_contracts`，将原输入／操作、owner、资源、执行目录和未决项投影为控制／状态／资源视图，并供模型修正与前端查看。此处只是既有规则结果的组织；下述逐操作一般算法、理论性质与调度研究主张仍未完整实现或证明。当前已落实的支持与正反例见[核验记录第 9 节](分析器共性缺口与验证.md#9-九来源反馈后的支持实现2026-10-31)。

本研究把 Harness 看作：**围绕模型能力和明确任务，组织输入、模型／服务、工具／检索、检查／修订、控制与结果的一段可定位执行过程及其必要上下文。** 分类对象是冻结版本、活动配置下的目标入口和候选边界。一个仓库可以同时包含防护、宿主、数据准备与评价，不能把仓库当作不可分的唯一类别。

这些特征并非一般程序绝无仅有。研究的领域针对性来自它们的共同组合：模型／索引初始化成本显著，原生对象及会话需要保留，模型输出可能决定下一轮工作，而任务质量需要独立判据。应研究这种组合造成的自动接入和调度困难，不主张发现了程序领域独有的新类型。

自动接入要求可以固定来源、活动配置和目标输入输出，找到原执行入口、资源来源及结果含义。原依赖不可见、动态反射或外部服务内部无法恢复时，记录未知及影响范围；能核对整体调用时保留整体，内部操作分别判断。**原库能运行只证明存在可行环境，不能推出任意内部函数脱离该环境仍能运行。**

不能承诺将无限制的任意仓库全自动转换为等价、可拆分的服务。限制应落在平台能够核对的程序形式及操作上，避免要求所有来源预先改写为同一框架。涉及服务的目标需要区分本平台可控制的实例与只能消费的外部端点。

## 2. 简化为两层，而不扩充一套庞大的类型表

第一层回答**“它在本任务中做什么”**：目标防护／补证、任务宿主、必要支撑、准备／训练／独立评价、展示／测试、未定。角色可多选，任务改变时角色可能改变。阶段采用输入检查、检索、模型调用、输出核查、反馈修订等阅读线索，不强制每个来源走同一流水线。

第二层回答**“它具有什么执行约束”**，收敛到三个契约维度：

| 维度 | 必须恢复的事实 | 对调度的直接含义 |
| --- | --- | --- |
| 控制 C | 输入输出、调用何时使能、返回给谁、分支／循环、等待／异常／取消、批次或会话范围 | 哪些请求已经能执行，在哪里真正交出控制，必须怎样接续与汇合 |
| 状态与效果 S | 对象及别名、读写集合、owner、共享文件／结果、缓存／续跑、外部副作用 | 哪些调用须保序、独占或同宿主，哪些结果才能算完成；未发现冲突不等于已证明独立 |
| 资源与生命周期 R | 配置来源和覆盖、模型／索引／客户端、初始化和清理、驻留、工作目录／环境、本地或远端 | 实际需要什么资源，何时加载、复用和释放；哪些占用平台能够控制并测量 |

函数、类、CLI、环境变量、配置对象是**恢复上述事实的程序形式**，用于选择分析配方；不再把它们与“防护用途”“可并行性”混作一个类别。例如 CLI 也能执行有状态多轮流程，HTTP 请求也可能产生不可重复副作用。

现有 `forms/families/traits/recipes` 可继续保存线索，`task_role` 保存角色声明；把线索汇合到 C／S／R 的检查结果即可，无需重建另一套平台层或立即更换所有字段。源码事实、语义假设、运行观测和未知分别保存，不能让 LLM 自报置信度代替检查。

## 3. 分类如何产生可用操作

```mermaid
flowchart LR
    A[冻结来源与任务目标] --> B[角色和程序形式线索]
    B --> C[恢复控制 状态 资源契约]
    C --> D[按请求操作检查义务]
    D --> E[有依据的边界 宿主和操作]
    D --> F[具体缺口及受影响操作]
    E --> G[结合当前使能与资源形成合法动作]
    G --> H[启发式或 RL 选择]
    H --> I[原实现执行与独立结果测量]
```

用一个表达式连接既有规则。设冻结证据为 E，候选边界为 b，宿主为 h，请求操作为 p；D(b,h,p) 是该操作按既有规则必须履行的义务，I 是当前确有构建与运行实现的操作集合：

`P_E(b,h) = {p ∈ I | D(b,h,p) 的每项义务均有有效依据，或由已实现且适用的运行守卫落实}`。

运行时可选集合还要收缩：

`A_t = {a | a 的操作属于 P_E，原控制已使能，owner／效果条件成立，当前资源及任务义务允许}`。

这两个集合区分“源码支持这个操作”和“此刻可以执行”。分类只选择调查与检查路径；调度器只能在后者中优化。未经核验的标签既不能直接发放许可，也不能直接作为排除一个来源的依据。

逐操作义务的重点不同：

| 请求操作 | 关键义务举例；不是完整 RuleSet |
| --- | --- |
| 整体接入 | 原参数／配置／环境闭合，资源和初始化可取得，结果与失败能交回 |
| 原流程内部交接 | 有实际拦截／接续位置，保留使能条件、返回、异常与相关状态 |
| 并行或重排 | 真实数据依赖满足，状态和外部效果无未处理冲突，owner 及顺序条件满足 |
| 准备、保留、释放或扩缩 | 实例由谁持有，初始化／销毁能兑现，在途引用与会话约束满足，资源账本对应真实动作 |

同一个未知不必阻塞所有操作。例如不能判断对象可跨进程传递，可能阻塞远程调用；若整体原生调用的独立义务已满足，可以保留整体。反之，不能定位某外部副作用的影响范围，就不能擅自断言它与某个并行操作无关。共享对象也不必然要求所有代码合并：应检查对象是否可变、原访问顺序及已有宿主规则。

算法可复用已有调查和修订流程：从原入口向外补齐 C／S／R；针对希望开放的操作展开义务；对未决项补读源码或选择已有支持的整体／宿主形式；核对后生成接线。失败结果返回“哪项义务、影响哪个操作、缺什么证据／实现”，让人工输入有明确落点。只增加分类标签而不改变这个流程，研究贡献会很弱。

## 4. 粒度选择与三个新来源的解释

目录条目、控制交接、资源实例是不同粒度。一组多个方法可以由同一个模型实例承载；一个整体 CLI 也可能处理多项输入。细化有价值，需要同时满足：存在可兑现的新选择，并且其等待／复用收益可能超过交接、物化、初始化及状态维护开销。成本估计用于排序候选，不能使非法边界合法。

| 来源 | 当前合理的起点 | 需要探索的细化及条件 |
| --- | --- | --- |
| TruFor | 保留原模型加载和推理脚本；两种脚本是实现变体 | 在保持一次加载和同一模型 owner 的前提下，是否能按图片交出执行权；逐图原失败和结果对应须保留。神经网络内部多个输出不自动产生有用的调度边界 |
| AnesSuite | 保留原评价宿主，分清服务消费和服务启动 | 按题调度须保留原线程并发、重试、汇合、文件续跑及评分；不能删除标签评分后将宿主当防护组件，也不能把服务端 GPU 当本地可释放资源 |
| PaperGraphBench | 区分准备、在线多轮评测、离线统计；保留原 controller | 在原轮次／服务调用使能点寻找交接，保留状态与判断导致的分支；已有数据不反复建图，未来轮次不提前派发 |

当前报告需要明确三类保留整体的原因：**行为约束要求、平台支持尚缺、暂未测得细化收益**。只有第一类能支持“此条件下不能这样拆”；后两类是研究和实现问题，不能伪装成理论结论。九来源的最新条目与操作证据见核验记录，不由本文预先批准上述细化。

## 5. 理论依据、最接近工作及创新边界

本轮做了面向机制的定向检索和原文核对，并非覆盖截至当日全部论文的系统综述。下表明确借鉴关系与尚未证明的区别。

| 一手依据及核对范围 | 借鉴什么 | 本研究需要额外解决什么 |
| --- | --- | --- |
| [Cousot：Abstract Interpretation in a Nutshell](https://www.di.ens.fr/~cousot/AI/IntroAbsInt.html)，作者理论说明 | 用有限抽象处理不可穷尽的执行，明确近似及未知 | 定义适用于受支持 Harness 形式的事实域、义务和保守边界；当前实现不能直接宣称是对完整 Python 的健全抽象解释 |
| [PyCG，ICSE 2021](https://arxiv.org/abs/2103.00587)，摘要及此前正文核对 | 跨过程赋值关系与调用目标恢复 | 还需配置优先级、对象生命周期、资源来源及实际控制交接；有调用图不等于可部署或可并行 |
| [IRIS，修订版 2025](https://arxiv.org/html/2405.17238v3)，第 3 节 | 静态工具提供候选与上下文，LLM 推语义规格，再分析和核对 | 原工作面向 Java 漏洞；这里只借鉴提议与分析分工，不能继承其结论为 Python 转换保证 |

| [Parrot，OSDI 2024](https://www.usenix.org/system/files/osdi24-lin-chaofan.pdf)，第 4.1—4.2 节 | 用 Semantic Function／Variable 表达应用依赖，将语义信息交给服务调度 | 这是最接近“结构信息服务调度”的对照。本文拟从已有程序恢复契约，并处理原生对象、配置和多种资源约束；不能将“首次语义感知调度”作为创新。Parrot 也处理运行时请求，不能把它误写为只支持固定静态图 |
| [Decima，SIGCOMM 2019](https://web.mit.edu/decima/)，项目说明及论文机制概述 | 用作业结构、资源和工作负载训练调度策略 | Harness 还有原 controller 的动态使能、对象 owner 与外部服务边界，不能直接把所有工作压成预知 DAG；需检验新表示是否提供额外收益 |
| [Clockwork，OSDI 2020](https://www.usenix.org/system/files/osdi20-gujarati.pdf)，摘要与引言 | 通过可控执行系统获得 DNN 服务的可预测性 | 提醒我们认真比较非学习调度；结构复杂或模型多不自动构成 RL 优势的证据 |

建议将核心主张收敛为：**从非标准已有 Harness 恢复面向调度操作的执行契约，按未决义务联合调整边界与宿主，输出可以实际兑现的调度自由度。**

这里的“最小充分”只能相对于指定操作与支持域而言：恢复足以核对该操作的事实，不试图理解整个库；目前尚未证明分析成本最小或划分全局最优。新意候选在于**恢复—逐操作核验—边界选择—实际调度**的具体连接及其效果，而不是 C／S／R 三个名字、已有调用图技术或加一个 RL 算法。它是对现有主设计的收敛，仍需更完整的相邻工作对照及实验证据才能确认新颖性。

可发展两项有限理论结果，与[数学规格 20](../../想法/20_形式化定义与证明义务.md)共用义务，不另起通用程序证明体系：

1. **证据精化的许可保留。** 在来源、环境、规则、义务集合固定，且新增证据与旧依据一致时，补证不应撤销已有静态许可；发生源码变化、矛盾或规则变更则须失效重检。运行时资源变化可以减少 A_t，不违反这一性质。这是检查器应满足的条件性性质，不能当作“分析越多必然可拆越细”。
2. **受支持变换的行为保持。** 对每条有限构造规则，在其控制、状态、初始化、效果及观察前提成立时，说明原执行与接入执行如何逐步对应，包括返回、失败、取消和必需结果。端到端测试提供具体实例证据，不能证明任意 Python 程序等价。方法替换或允许策略省略干预时，应另用任务质量约束评价，不能继承保真结论。

## 6. 如何连接现有调度和 RL

契约生成合法动作与运行约束；真实执行提供成本和负载估计。策略观测可包含已经使能的位置、就绪等待时间、原依赖、owner 归属、已观测服务时间、资源需求、冷／热实例和实际可用容量。角色／阶段帮助表达任务关系，但不能代替实时状态；参考答案、未来分支和最终评分不能泄漏到决策前。

学习的动机是可测量的跨时段权衡：保留一个热模型可减少后续加载，却占用其它任务所需内存；优先短调用可能改善均值，却推迟长会话的必要后续。不同耗时与动态分支使决策发生在事件点，现有 joint/1 可承接合法派发及已获准生命周期动作。静态分类本身既不保证观测满足马尔可夫性，也不能证明 RL 优于调参启发式。

主实验仍采用[协议第 15 节](../../ccfa-workfiles/experiments/harness-paper-design/plan.md#15-多来源防护效果保持与资源调度主实验2026-10-28)：在固定原防护路径、模型和必需工作量下，保持各任务质量并改善资源／时延。各质量指标分别约束，不将不同场景的 accuracy、F1 等直接混为一个分数；成本包括加载和失败消耗。外部 API 费用与等待单列，无法观测其 GPU 成本时记未知。

沿用 B0 原生、B1 平台整体 FIFO、B2 调参启发式、B3 相同动作和观测的 RL，以及 D 同原区域粗细配对。不新建模拟实验平台。D 回答分析器是否产生有用控制；B2／B3 回答学习是否有效利用控制，两者不能互相代替。如果仅整体排队已有收益，应按整体调度贡献报告；如果启发式足够好，应收缩 RL 主张。

分类／分析机制的补充对照也在同一批真实来源上进行：同分析模型和预算条件下比较现有线索与契约引导，统计目标入口可用性、错误放行、未决原因准确性、人工动作／时间及分析费用。再看获准内部交接／生命周期动作是否真实执行。被用于修规则的三库属于开发样例，不能随后称为未见测试库；按新的程序结构／来源版本留出验证，不能只随机打散同库函数。

## 7. 与当前平台的差距及实施顺序

当前已经具备源码分类线索、用途声明、有限参数流、逐操作报告和 joint/1 接口，适合在这些位置补齐。尚缺完整的配置／原进程上下文恢复、可核对的完成契约，以及从分类证据到调度操作的统一归纳。没有必要先创造更多类别或为各库单独写包装。

第一优先级是[核验记录 8.4](分析器共性缺口与验证.md#84-现在优先补什么)中的候选完整性、原调用环境、有限配置流和真实结果检查。然后把每个边界已具备／未具备的 C／S／R 条件与现有操作报告对应，展示为什么整体保留、细化卡在哪里。最后用同一真实区域的 D 配对验证实际新增控制，再进入既有多来源混合调度对照。

交付应能回答：“选哪一个目标入口；输入怎么传；缺哪项配置或资源；当前能做哪些操作；为什么暂不能细拆；怎样确认本次真的完成。”这比仅给类别、拆分数量或一个静态 READY 更接近可检验的研究结果。
