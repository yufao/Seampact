# 0.15.7 实验启动存储接线

2026-11-03 的本地接线修复记录；当时远端健康接口为 0.15.6。后续本地工作树的逐操作契约、预算策略及部署状态以[当前实现](../设计与实现/当前实现.md)为准。

真实研究节点已完成 RefChecker worker 的构建与发布，随后镜像保留准备在读取平台自身容器的挂载时返回 `DOCKER_UNKNOWN`。操作者核实：更新保留的旧 hostname 已不对应当前容器，且平台只有数据、来源与 Docker socket 挂载，没有用于实际存储空间核验的 Docker 存储挂载。没有启动本轮 RL 任务，不能将此故障计为来源推理失败。

修复位于原部署和镜像模块：

- `deploy.sh update --with-tools` 给平台写入稳定的容器名称，保留原 hostname、网络和业务配置。工具接线从所选 daemon 的真实 `DockerRootDir` 增加只读 `/seampact-docker-storage` 挂载，已存在的同目标挂载必须对应相同来源且只读。
- 镜像空间检查使用上述明确容器名称与平台可见路径；仍核对实际 bind 来源等于 daemon 存储目录，再读取该文件系统空间。没有取消核验或将未知空间填为足够。
- 更新时只允许本次工具接线明确新增的 socket／只读探针挂载，原数据及其他持久挂载仍须逐项一致。未使用工具接线的外部部署须自行提供可核对挂载，见[操作说明](../部署与操作/实验镜像保留与备份.md)。

核验：镜像保留 30 项、部署工具／恢复 7 项、部署预检 4 项，合计 **41 项通过**，其中新增 4 项覆盖旧 hostname、真实映射文件系统的空间读取、冲突／非只读挂载拒绝及不相关文件系统拒绝。Docker 操作采用替身，没有在目标节点运行修复后的接线。

仅就本次接线修复快照而言，修复前后的 worker、checker 执行闭包一致；当时新 worker 的 43 项文件在 LF 规范化后与该快照匹配。后续逐操作契约修改已改变执行闭包，不能将此历史匹配推广到当前工作树；按当前规则重检并构建匹配工件，无需仅因更新重复九库模型分析。训练清单仍冻结实际协调器代码、策略和资源。更新后必须由正常准备通过才进入运行，不能据旧身份匹配宣布 RL 成功。

用户提交推送后，在 Linux 代码目录按现有入口执行：

```bash
bash deploy.sh update --with-tools
```

本轮不改来源算法、原对象、W／H／R、生命周期资格、调度理论或学习器；没有产生新的模型预测、参数更新或资源收益结论。
